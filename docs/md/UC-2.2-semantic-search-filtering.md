# UC-2.2 Semantic Search & Filtering

**Use Case ID:** UC-2.2

**Use Case Name:** Semantic Search & Filtering

**Actor(s):** Contributor, Moderator, Administrator — every read endpoint on `MediaAssetController` (`list`, `search`, `get`, `history`) is `@PreAuthorize("isAuthenticated()")`, and the controller's own class javadoc literally reads "REST endpoints for UC-2.2: Media library browsing" — confirming this UC number independently. Not Contributor/Administrator-only.

**Precondition(s):** The actor is authenticated with an active session. The institution media library exists (UC-1.2, UC-2.1). Confirmed accurate.

## Main Flow

1. The actor navigates to the Media Library from the workspace sidebar.
2. The system displays all media assets for the actor's institution in a grid view, grouped/filterable by album. Confirmed accurate — each `AssetCard` shows the asset code, title (see correction — this is the filename, not a distinct title field), upload date, file size + type, and either a "Processing…" badge or the asset's first AI-classified tag as a category-style chip.
3. The actor browses using text search, an album filter, sort (`newest`/`oldest`/`name`/`size` — exact match to Newest/Oldest/Name/Size), and a grid/list view toggle (`viewMode`). **Text search covers far less than claimed** — see the correction below; "event name" and "uploader" are not searchable as free text at all, and neither is a tag added after upload (A3).
4. The result strip updates with the matching count. **Not in the "0 of [N] assets" format** — the actual copy is `"{N} folders · {M} items"` (or `"{M} results"` while searching), with no total-before-filtering denominator shown.
5. The actor clicks an asset card to open the Asset Detail Panel: media preview, asset code (read-only) and title, metadata grid (filename, uploader + institution, upload date, album, file size, resolution/duration, file type — all confirmed present), an AI Tags block with per-tag confidence percentages, a "Your tags" block with an add-tag field, and a "Used In" list (`usedIn`, full history in `/{id}/history` — UC-2.3 per this doc's own reference, though CLAUDE.md's Module 2 index currently labels UC-2.3 as Notifications; not re-verified this session).
6. From the panel, the actor may click **"New Submission"** (this UC's "Use in New Social Media Post") or **"Add to Draft"**. Confirmed: "New Submission" is unconditionally available to all three roles — it's a pure client-side `navigate("/submissions/new?assetIds=...")`, no backend role check in the path actually used. **"Add to Draft" is Contributor-only, but only because the frontend hides the button for other roles** (`canAddToDraft={user.role === "contributor"}`) — the API call it actually makes (`POST /submissions/{id}/assets`, i.e. the same `attachAsset` the composer itself uses) is open to all three roles. The backend's own dedicated `POST /media-assets/{id}/use-in-new-post` and `/{id}/add-to-draft` endpoints — both genuinely `hasRole('CONTRIBUTOR')` — are dead code from this screen; neither is ever called by the current frontend.

## Alternative Flows

- **A1 — No Results Found:** confirmed in spirit, wrong exact copy. The empty state reads **"No assets match your filters"**, not `"0 of [N] assets"`; active filters remain visible and clearable either way.
- **A2 — Cross-Institution Access Attempt:** confirmed for the 404 half — `MediaAssetService.get()` throws `404` for a non-network-role actor requesting an asset outside their visible institutions (own + shared default), and Postgres RLS exists on `media_assets` as a second layer (not re-verified policy-by-policy this session). **Network View is Moderator + Administrator, not Administrator-only** (`isNetworkBrowser = user.role === "admin" || user.role === "moderator"`) — same recurring pattern as every other UC this session (Moderator is network-wide). **The audit-logging claim is false.** The Network View banner literally says *"This session is being logged in the access audit log (BR-MED-01)"*, but no such logging exists anywhere in the backend — `recordAssetAudit` is only ever called for delete, bulk-delete, upload, move, tag-add, and tag-remove (write actions); there is no audit event for activating Network View, for a cross-institution browse, or for any read/view action at all. This is a real, user-facing discrepancy: the UI asserts something is happening that isn't.
- **A3 — Custom Tag Added:** **the "searchable by text search" half is false.** Adding a tag (`MediaAssetService.addTag`) never triggers re-embedding, and neither search path queries the `asset_tags` table at all: the plain `list()` endpoint's `query` filter only checks `fileName`/`assetCode`, and the `/search` endpoint's keyword fallback (`matchesKeyword`) only checks `fileName`, `assetCode`, `aiDescription`, `aiCategory`, and `aiTags` (the AI-classification tag array on `MediaAsset` itself) — never the manually-added `AssetTag` rows. A tag added through the Asset Detail Panel is invisible to both search paths, permanently. (A manual tag present *at upload time* does get folded into the classification-time embedding text via `AIClassificationService.buildEmbeddingText`, so it can contribute to semantic ranking for that one embedding generation — but adding one afterward changes nothing, since nothing ever re-embeds.) Institution-scoping of tags is otherwise accurate — every query here is already institution/visibility-scoped upstream.
- **A4 — Add to Existing Draft, No Active Drafts:** confirmed closely. `AddToDraftModal` shows "No drafts yet — Start a new post with the selected media instead" plus a "New Post" button when the Contributor has no `draft`-status submissions; the footer's "New Post instead" ghost button is hidden in this state (nothing else duplicated).
- **A5 — Add to Existing Draft, Asset Limit Reached:** confirmed in effect, different mechanism than "inline error." The 10-media-per-submission cap (`SubmissionService.MAX_MEDIA_PER_SUBMISSION`) is enforced server-side and surfaces as a **toast**, not an inline message inside the modal. Because `handleSelectDraft` attaches a multi-selection one asset at a time in a loop and only swallows a `409` (already-attached) per iteration, any *other* error (including hitting the limit) stops the loop immediately — assets attached earlier in that same batch stay attached; the one that failed, and any after it, are not appended.

## Postcondition(s)

The actor has located and, if applicable, reused a media asset; the asset's detail view accurately reflects its current metadata, AI tags, album, and available actions. Confirmed accurate, with the caveat that "title" here always means the original filename — there is no distinct, editable title.

## Corrections from the prior draft of this UC

- **Actors:** added Moderator — every read/browse endpoint is `isAuthenticated()`, and Network View (A2) is explicitly Moderator + Admin, not Admin-only.
- **"Editable title" doesn't exist.** `AssetDetailPanel` renders the title in a `<div className="med-editable-title">` — the CSS class name is misleading; it's a plain, non-interactive text node (no click handler, no input, no `contentEditable`). There's also no rename endpoint on `MediaAssetController` for an asset's display name — "title" is always `fileName`, permanently, from upload onward.
- **Text search covers far less than described.** "Filename, tag, event name, uploader" is only accurate for "filename." Tag search only covers AI-generated tags (via `aiTags`/`aiCategory`/`aiDescription`), never manual ones (A3). "Event name" isn't a field on `MediaAsset` at all — nothing to search. "Uploader" exists only as an exact-match `uploaderId` filter parameter on the plain `list()` endpoint (a picker value), not as typed free text in the search box the UI actually wires up (which calls `/search`, not `list()` with a query string).
- **A3's core claim is false** — a custom tag is not searchable, ever, by either search path. See above.
- **A2's audit-logging claim is false** — the UI says Network View activation is logged; nothing logs it.
- **"Add to Existing Draft (Contributor only)" is a frontend-only restriction**, not a backend one. The call path actually used (`attachAsset`, shared with the composer) is open to all three roles; the two backend endpoints that *are* genuinely Contributor-restricted (`/use-in-new-post`, `/add-to-draft` on `MediaAssetController`) are unused dead code.
- **A5's "inline error" is a toast**, and a multi-asset "Add to Draft" batch is not atomic — an asset-limit failure partway through a batch leaves the earlier successful attachments in place.
- **Result-count and empty-state copy don't match** the "0 of [N] assets" phrasing — see A1 and Main Flow step 4.
