# UC-2.2 Semantic Search & Filtering

**Use Case ID:** UC-2.2

**Use Case Name:** Semantic Search & Filtering

**Actor(s):** Contributor, Moderator, Administrator — every read endpoint on `MediaAssetController` (`list`, `search`, `get`, `history`) is `@PreAuthorize("isAuthenticated()")`, and the controller's own class javadoc literally reads "REST endpoints for UC-2.2: Media library browsing" — confirming this UC number independently. Not Contributor/Administrator-only.

**Precondition(s):** The actor is authenticated with an active session. The institution media library exists (UC-1.2, UC-2.1). Confirmed accurate.

## Main Flow

1. The actor navigates to the Media Library from the workspace sidebar.
2. The system displays all media assets for the actor's institution in a grid view, grouped/filterable by album. Confirmed accurate — each `AssetCard` shows the asset code, title (see correction — this is the filename, not a distinct title field), upload date, file size + type, and either a "Processing…" badge or the asset's first AI-classified tag as a category-style chip.
3. The actor browses using text search, an album filter, sort (`newest`/`oldest`/`name`/`size` — exact match to Newest/Oldest/Name/Size), and a grid/list view toggle (`viewMode`). Text search now covers filename, asset code, uploader email, and **every tag — manual or AI-generated** (fixed 2026-09-13, see A3). "Event name" is still not searchable — it isn't a field on `MediaAsset` at all.
4. The result strip updates with the matching count. **Not in the "0 of [N] assets" format** — the actual copy is `"{N} folders · {M} items"` (or `"{M} results"` while searching), with no total-before-filtering denominator shown.
5. The actor clicks an asset card to open the Asset Detail Panel: media preview, asset code (read-only) and title, metadata grid (filename, uploader + institution, upload date, album, file size, resolution/duration, file type — all confirmed present), an AI Tags block with per-tag confidence percentages, a "Your tags" block with an add-tag field, and a "Used In" list (`usedIn`, full history in `/{id}/history` — UC-2.3 per this doc's own reference, though CLAUDE.md's Module 2 index currently labels UC-2.3 as Notifications; not re-verified this session).
6. From the panel, the actor may click **"New Submission"** (this UC's "Use in New Social Media Post") or **"Add to Draft"** — **both open to all three roles** (confirmed as the intended design, corrected 2026-09-13). "New Submission" always was: a pure client-side `navigate("/submissions/new?assetIds=...")`, no backend role check in the path actually used. "Add to Draft" now is too — `AssetDetailPanel`'s `canAddToDraft` was previously hardcoded to `user.role === "contributor"`, hiding the button from Moderator/Admin even though the API call it makes (`POST /submissions/{id}/assets`, the same `attachAsset` the composer itself uses) was always open to all three roles; the button is unconditional now. The backend's own dedicated `POST /media-assets/{id}/use-in-new-post` and `/{id}/add-to-draft` endpoints — both genuinely `hasRole('CONTRIBUTOR')` — remain dead code from this screen; neither is ever called by the current frontend.

## Alternative Flows

- **A1 — No Results Found:** confirmed in spirit, wrong exact copy. The empty state reads **"No assets match your filters"**, not `"0 of [N] assets"`; active filters remain visible and clearable either way.
- **A2 — Cross-Institution Access Attempt:** confirmed for the 404 half — `MediaAssetService.get()` throws `404` for a non-network-role actor requesting an asset outside their visible institutions (own + shared default), and Postgres RLS exists on `media_assets` as a second layer (not re-verified policy-by-policy this session). **Network View is Moderator + Administrator, not Administrator-only** (`isNetworkBrowser = user.role === "admin" || user.role === "moderator"`) — same recurring pattern as every other UC this session (Moderator is network-wide). **The audit-logging claim is fixed (2026-09-13).** It was false — the Network View banner asserts *"This session is being logged in the access audit log (BR-MED-01)"*, but `recordAssetAudit` was only ever called for writes (delete, bulk-delete, upload, move, tag-add, tag-remove), never for a read/browse/Network-View-activation. Now `POST /media-assets/network-view/log` (`MediaAssetService.logNetworkViewAccess`, `hasAnyRole('MODERATOR','ADMIN')`) records `MEDIA_NETWORK_VIEW_ACCESSED`, fired once per browser session from `MediaRepositoryScreen` (a `sessionStorage` flag guards the repeat calls, not once per Network View "activation" — see the note below on there being no actual toggle).
- **A3 — Custom Tag Added: fixed (2026-09-13).** It was false that a custom tag was searchable — `addTag` never triggered re-embedding, and neither search path queried the `asset_tags` table at all. Both `list()`'s `query` filter and `/search`'s keyword fallback (`matchesKeyword`) now batch-fetch every tag (manual or AI-generated) per candidate asset (`MediaAssetService.loadAllTagLabels`, one query via `AssetTagRepository.findLabelsByMediaAssetIds`, not N+1) and match the query text against them. A custom tag is searchable immediately after being added — no re-embedding needed, since this is a keyword match, not semantic ranking. (Semantic *ranking* still only reflects manual tags present at the asset's original classification time, via `AIClassificationService.buildEmbeddingText` — a tag added afterward influences the keyword-fallback layer, not the vector similarity ordering. Re-embedding on every tag edit was considered and skipped as materially larger scope — it would add a synchronous or async Voyage AI round-trip to every tag add/remove.) Institution-scoping of tags is otherwise accurate — every query here is already institution/visibility-scoped upstream.

**Note found while fixing A2:** there is no actual Network View *toggle* — `networkView = isNetworkBrowser` is `true` for the entire session for any Moderator/Admin, permanently; there's no on/off switch, so the banner is always showing for those roles rather than appearing only after a deliberate activation. Not changed as part of this fix; flagged for awareness since it affects how literally to read "activate a Network View toggle" in the Main Flow/A2 text.
- **A4 — Add to Existing Draft, No Active Drafts:** confirmed closely, and now applies to any actor, not just a Contributor (see Main Flow step 6). `AddToDraftModal` shows "No drafts yet — Start a new post with the selected media instead" plus a "New Post" button when the actor has no `draft`-status submissions; the footer's "New Post instead" ghost button is hidden in this state (nothing else duplicated).
- **A5 — Add to Existing Draft, Asset Limit Reached:** confirmed in effect, different mechanism than "inline error." The 10-media-per-submission cap (`SubmissionService.MAX_MEDIA_PER_SUBMISSION`) is enforced server-side and surfaces as a **toast**, not an inline message inside the modal. Because `handleSelectDraft` attaches a multi-selection one asset at a time in a loop and only swallows a `409` (already-attached) per iteration, any *other* error (including hitting the limit) stops the loop immediately — assets attached earlier in that same batch stay attached; the one that failed, and any after it, are not appended.

## Postcondition(s)

The actor has located and, if applicable, reused a media asset; the asset's detail view accurately reflects its current metadata, AI tags, album, and available actions. Confirmed accurate, with the caveat that "title" here always means the original filename — there is no distinct, editable title.

## Corrections from the prior draft of this UC

- **Actors:** added Moderator — every read/browse endpoint is `isAuthenticated()`, and Network View (A2) is explicitly Moderator + Admin, not Admin-only.
- **"Editable title" doesn't exist.** `AssetDetailPanel` renders the title in a `<div className="med-editable-title">` — the CSS class name is misleading; it's a plain, non-interactive text node (no click handler, no input, no `contentEditable`). There's also no rename endpoint on `MediaAssetController` for an asset's display name — "title" is always `fileName`, permanently, from upload onward. **Not fixed** — a real rename feature needs a schema decision (a new `displayTitle`-style column vs. repurposing `fileName`) that's bigger scope than the other corrections here; flagged for a decision rather than built unprompted.
- **A3 and A2's false claims are now fixed** — see above. Text search now covers filename, asset code, uploader email, and every tag (manual + AI). "Event name" still isn't searchable — it isn't a field on `MediaAsset` at all, so there's nothing to wire up without a larger change (joining through to submission event titles that used the asset).
- **"Add to Existing Draft (Contributor only)" was wrong, and has been fixed (2026-09-13).** It's confirmed intended to be open to all three roles — the call path it uses (`attachAsset`, shared with the composer) always was. `AssetDetailPanel`'s `canAddToDraft` prop is no longer hardcoded to `user.role === "contributor"`; the button now shows for any role. The backend's genuinely Contributor-restricted `/use-in-new-post`/`/add-to-draft` endpoints on `MediaAssetController` remain unused dead code — not removed, since deleting working (if unused) code wasn't asked for.
- **A5's "inline error" is a toast**, and a multi-asset "Add to Draft" batch is not atomic — an asset-limit failure partway through a batch leaves the earlier successful attachments in place. Not changed — UX polish, not a functional gap.
- **Result-count and empty-state copy don't match** the "0 of [N] assets" phrasing — see A1 and Main Flow step 4. Not changed — copy-only.
