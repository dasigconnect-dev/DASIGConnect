# UC-2.5 Automated Watermarking

**Use Case ID:** UC-2.5

**Use Case Name:** Automated Watermarking

**Actor(s):** Administrator (configuration, write); any authenticated role (read, to render post previews). `WatermarkConfigurationService.authorizeWrite`/`authorizeRead` confirm this exactly.

**Precondition(s):** For configuration: the actor is an authenticated Administrator. For application: a submission containing at least one photo is being published (not "approved" — see Automatic Application step 1 below, a real correction from an earlier draft of this UC).

## Main Flow — Watermark Configuration

1. An Administrator navigates to Page Settings and opens the Watermark configuration panel: a transparent canvas editor with 1:1/4:5/16:9 aspect-ratio preview toggles — confirmed accurate (`WatermarkCanvasEditor.tsx`).
2. The Administrator adds up to 3 elements — image, text, or shape (rectangle/line) — confirmed accurate (`WatermarkConfigurationService.save`'s `@Size(max = 3)` validation, enforced again server-side in `sanitizeElements`). Each element is positioned/sized as percentage coordinates and can be dragged/resized.
3. The Administrator previews across aspect ratios — confirmed accurate.
4. The Administrator saves; the system stores each element's position/size as percentage values plus type-specific properties (image reference, text content/font, shape type/color) — confirmed accurate, serialized as JSON in `watermark_configurations.elements_json`.
5. **Removed (2026-09-17): there is no institution-specific watermark override.** An earlier draft of this use case described an Administrator selecting a specific institution and saving a distinct watermark design that would take precedence over the network default for that institution's submissions. This was never functional — `WatermarkConfigurationService.get()`/`.save()` always read/wrote the single global config regardless of any institution id passed in, and `WatermarkApplicationService.resolveConfiguration()` never looked at the submission's institution either. The dead scaffolding (`WatermarkConfigurationRepository.findByInstitutionId`, the request/response DTOs' `institutionId`/`institutionName`/`isOverride` fields, the frontend's unused `institutionId` plumbing through `watermarkApi`/`useWatermarkConfiguration`, and the orphaned `WATERMARK_OVERRIDE_REMOVED` audit action) has been removed. The watermark is now honestly a single, network-wide configuration — there is no per-institution step 5/6, and no A3.

## Main Flow — Automatic Application

1. **Corrected (2026-09-17): watermarking happens at publish time, not at approval.** The original draft's step 1 read "Upon an Administrator approving a submission... the system checks each attached media asset's file type." In the actual implementation, nothing happens at approval — the check and render happen inside `FacebookPublisherService.publishMediaLinks()` → `WatermarkApplicationService.resolvePublishUrl()`, called at the moment of the actual Facebook publish attempt (immediately for Fast-Track, or at the scheduled time for a Standard submission). Practical effect: editing the watermark configuration between approval and a Standard submission's scheduled publish time **does** affect that already-approved, not-yet-published post — this is different from (and arguably safer than) "future approvals only."
2. For each photo asset (JPEG/PNG/GIF/WebP — not just a generic "photo"; `isWatermarkable()`), the system reads the network watermark configuration, reads the photo's actual dimensions, and renders all configured elements at their proportionally scaled positions — confirmed accurate.
3. The watermarked version is generated and used for publishing; the original unwatermarked asset stays in the media library — confirmed, with one nuance: the watermarked copy is **not** a `media_assets` row. It's a transient object-store blob (`generated/watermarked/{submissionId}/{assetId}-{timestamp}.jpg`, `MediaStorageService.generatedWatermarkPath`) uploaded solely to hand Facebook a URL — it never appears in the Media Library UI, and nothing purges it later (`MediaStorageService`'s own comment on its usage-sweep method calls these out as storage-cost orphans alongside other unlinked objects).
4. Video assets are published without any watermark — confirmed accurate (`isWatermarkable()` excludes video entirely; `publishMediaLinks` only builds `photoPublishUrls` for images).

## Alternative Flows

- **A1 — No Watermark Configured — behaves differently than described.** The draft says the system "publishes photos without a watermark and logs a configuration gap." What actually happens: `resolvePublishUrl` falls back to `createDefaultFallbackConfig()` — a hardcoded text watermark (`"@DASIGCentralVisayas"`) baked into the code, not read from the DB — when no config row exists at all. A submission is only ever published genuinely unwatermarked if a config row exists **and** is explicitly disabled (`enabled = false`). There's no "configuration gap" log distinct from normal operation either way.
- **A2 — Update Existing Watermark Design:** confirmed for "applies to future publishes," but see Automatic Application step 1 above — "future approvals only" is not quite right, since the config is re-read live at every publish attempt, not frozen at approval time.
- **A3 — Remove Institution-Specific Override: removed (2026-09-17), see Configuration step 5.** There was never an institution-specific override to remove.
- **A4 — Watermark Application Failure: implemented 2026-09-17 (previously silent).** Rendering failure — an undecodable image, a download error, any exception in the render pipeline — is non-blocking by design (the post still publishes with the original, unwatermarked image, since a missing brand mark is a much smaller problem than a missed scheduled post). It used to be *silently* non-blocking: the exception was caught and logged server-side only (`log.warn`), with no audit trail and no Administrator notification. Now every failure records an immutable `PUBLISH_WATERMARK_FAILED` audit entry (`AuditLogService`, `PUBLISHING` category) and fires `WatermarkApplicationFailedEvent`, which `NotificationEventListener.onWatermarkApplicationFailed` turns into an in-app + email notification to every Administrator, linking back to the affected submission. Publishing itself is still never held up waiting for this — matching the draft's underlying intent ("logs the failure, notifies the Administrator") without adopting its "holds the affected submission's publishing step" clause, which would have turned a cosmetic problem (an unbranded post) into a functional one (a late or missed post) for something as minor as a bad watermark image.
- **A5 — Mixed-Media Submission:** confirmed accurate — only photo assets are watermarked; video publishes watermark-free, same mechanism as the main flow.
- **A6 — Per-Asset Watermark Opt-Out:** confirmed real and working — `link.isSkipWatermark()` is checked first thing in `resolvePublishUrl`, before any configuration lookup or rendering happens.
- **A7 — Unusual Aspect Ratio: not implemented.** There's no aspect-ratio-outlier detection anywhere in `drawElement`/`drawText`/`drawShape`/`drawImage` — the percentage math is applied unconditionally regardless of how far the photo's aspect ratio is from what the design was previewed against, and nothing is flagged for Administrator review. `drawImage` does have its own "don't stretch, fit within the box" logic for an image element specifically (contain-style scaling with anchor-based positioning), but that's a per-element rendering detail, not aspect-ratio-outlier detection on the photo being watermarked.

## Postcondition(s)

Approved photo submissions carry the network watermark design (rendered proportionally to each photo's dimensions) in their published version at the moment they actually publish, except assets marked for opt-out; original unwatermarked assets remain in the media library. Videos publish without a watermark. A rendering failure publishes the original image and now (2026-09-17) always leaves an audit trail and notifies every Administrator. There is no institution-specific watermark tier.

## Not in the original draft at all

- GIF and WebP are watermarkable too, not just a generic "photo" (`isWatermarkable`: jpeg/png/gif/webp).
- `WATERMARK_CONFIG_UPDATED` is fully audit-logged with actor, element count, and enabled state.
- An image element's `imageUrl` can reference an institution logo automatically via a special `/api/v1/institutions/{id}/logo` URL pattern, or fall back to the submitting institution's logo when no explicit image URL is set at all (`drawImage`'s `INSTITUTION_LOGO_PATTERN` handling and its final fallback branch) — not mentioned anywhere in the draft.

## Generated watermark cleanup, fixed 2026-09-17

The watermarked derivative uploaded to `generated/watermarked/{submissionId}/{assetId}-{timestamp}.jpg` used to live outside the `media_assets` retention/purge lifecycle entirely — nothing ever cleaned it up, and it accumulated in R2 forever. A new `GeneratedWatermarkPurgeJob` (daily, `app.watermark.purge-cron`, default `0 45 2 * * *` UTC) sweeps that prefix and deletes anything older than `app.watermark.generated-retention-days` (default 3 days — Facebook only ever fetches the URL once, at publish time, so a short window is safe). `MediaStorageService.purgeExpiredGeneratedWatermarks(Duration)` does the actual `ListObjectsV2` sweep + delete, best-effort per object (one failed delete doesn't abort the rest of the sweep); registered in `ManualJobRunner` and `SystemHealthService.EXPECTED_JOBS` like every other background job, so it's on-demand runnable and monitored the same way.

## Known limitations (not changed this pass)

- A1's hardcoded fallback and A7's lack of aspect-ratio flagging are both left as-is — both are product-scope decisions (what should truly-unconfigured or badly-cropped watermarking look like), not bugs, and weren't asked to be built this pass. (The Watermark Studio's 1:1/4:5/16:9 preview toggle already covers previewing a design across common aspect ratios — confirmed still accurate, see Configuration step 1 — so there was nothing missing there.)
