# UC-3.5 System Health Analytics

**Use Case ID:** UC-3.5

**Use Case Name:** System Health Analytics (the admin System Health screen).

**Actor(s):** Administrator — confirmed exactly: `SystemHealthController` is class-level `@PreAuthorize("hasRole('ADMIN')")`, no other role can reach any endpoint on this screen.

**Precondition(s):** The actor is authenticated with Administrator privileges.

## Main Flow

1. Confirmed — the actor navigates to System Health from the admin console, a real screen genuinely separate from both the Analytics dashboard and the Resolution Center (see the numbering note in the footer — this SRS number collides with a *third*, unrelated feature this codebase already calls "UC-3.5").
2. Current infrastructure/operational health:
   - **Storage capacity: confirmed real and close to the draft.** Database storage via `pg_database_size(current_database())`; media storage via a live Cloudflare R2 bucket scan (`MediaStorageService.probeUsage()`, counting every object including watermarked derivatives and orphans), falling back to a DB byte-sum estimate only if the object-store probe fails. Both are measured against configurable platform-tier limits (`app.system-health.database-limit-bytes`/`media-limit-bytes`), whose defaults track the actual free-tier caps named in the SRS's own constraints section — Supabase Postgres 500 MB, Cloudflare R2 10 GB.
   - **API connection status: confirmed real for all four named services, with one caveat.** Facebook Graph API: genuine token-status lookup with a real expiry countdown (`Duration.between(now, expiresAt)`), not just valid/invalid. Anthropic Claude and Voyage AI: both real, but shallow — a `HEAD` reachability probe against the API's base URL plus a check that an API key is configured, not an actual authenticated capability call; a `5xx` response is unhealthy, anything else (including a `4xx` from lacking real auth on a bare `HEAD`) counts as reachable. Email Service Provider: the same shallow reachability probe against the configured mail API base URL (Resend).
   - **Background job health: real, and the tracked list is much larger than the draft's four named examples.** 15 jobs report into `ScheduledJobHealthService`'s tracking table (`EXPECTED_JOBS`), not just the four named in the draft — `PublishingSchedulerJob`, `ReviewLockCleanupJob`, `StaleSubmissionDetectorJob`, `AbandonmentDetectorJob`, `TokenPublishingEscalationJob`, `ValidationDeadlineNotificationJob`, `EmbeddingReconciliationJob`, `SocialEngagementSyncJob`, `MediaAssetRetentionPurgeJob`, `GeneratedWatermarkPurgeJob`, `StaleDraftSlotReleaseJob`, `TokenHealthCheckJob`, `ScheduledJobRunRetentionJob`, `EmbeddingFailureDigestJob`, `EmptyScheduleWarningJob`. Each job's expected interval is known (1 minute up to weekly), and a job is only flagged stale once its last run is more than *twice* its expected interval old — a weekly job isn't permanently marked unhealthy just for being quiet most days.
   - **Operational health metrics: an exact match to the draft's five named metrics**, and genuinely computed here (not merely reused from the Analytics dashboard, though `publish_success_rate` deliberately shares the exact same calculator Analytics uses, so the two screens can never disagree on that one number) — approval turnaround time (hours), Edit & Approve rate (percent of approvals where the reviewer edited before approving), manual fallback resolution rate (completed ÷ started manual-publish workflows), publish success rate, and Live Event Fast-Track submission volume, all over a rolling 30-day window.
3. **Drill-in: partially aspirational.** No per-institution storage breakdown exists anywhere (no query, no endpoint). No job *execution history* exists either — `ScheduledJobRunRepository` only ever exposes the single latest run per job (`findTopByJobNameOrderByStartedAtDesc`/a latest-per-job batch query); there's no history-listing query or endpoint at all, so "drill in for recent job execution history" doesn't correspond to anything real. What *does* exist, and isn't in the draft at all: a genuine **"Re-run" button per job**, letting an Admin manually trigger any tracked job on demand (`POST /system-health/jobs/{jobKey}/run`, audit-logged as `BACKGROUND_JOB_RUN`) instead of waiting for its schedule.
4. **Threshold warnings: real mechanism, different presentation than "flags."** Storage status genuinely changes color/status at configurable thresholds (`storage-warning-threshold-percent` default 80, `storage-critical-threshold-percent` default 95 — matching the draft's own "e.g. 80%" example precisely), rendered as a colored usage meter bar per storage type, always visible on the card itself rather than a separate flag that appears only near the threshold. Same visual-status pattern applies to jobs, services, and operational metrics — a consistent `HEALTHY`/`WARNING`/`UNHEALTHY`/`UNAVAILABLE`/`SCHEDULED` status vocabulary throughout the whole screen, not just storage.

## Alternative Flows

- **A1 — Metric Unavailable: confirmed accurate.** `HealthStatus.UNAVAILABLE` is a genuine, distinct status from `UNHEALTHY` — used whenever a metric's own query throws (DB unreachable, R2 probe fails and DB fallback also fails, no Facebook token configured at all, an external API key missing, a job that has never once run and isn't due to run again for a long time) — never silently reported as a false healthy or unhealthy reading.
- **A2 — Storage Threshold Warning: real threshold, not literally a "persistent banner."** The 80%/95% thresholds are real and configurable (see Main Flow step 4). What renders is an inline colored status on the storage card itself (and its contribution to the overall page status at the top), not a separate banner component — functionally similar (it's visible for as long as the condition holds, every time the screen is open) but not the same UI element the draft's wording implies.
- **A3 — Background Job Failure Detected: confirmed accurate, including the draft's own hedge.** A failed or stale job is flagged `UNHEALTHY`/`WARNING` in the job list. There is genuinely no job-failure-specific notification trigger anywhere in `NotificationEventType` (29 values, none job-related) — so per the draft's own fallback clause ("alerts the Administrator, if one exists... otherwise visible only on this screen"), the actual behavior is screen-only, which the draft already allows for rather than contradicts.
- **A4 — Export System Health Snapshot: confirmed real.** `GET /system-health/export` returns a genuine point-in-time CSV snapshot of every storage/service/job/operational-metric row, audit-logged as `SYSTEM_HEALTH_EXPORTED`. Worth flagging for hardening, not currently exploitable: the CSV builder's own escaping helper (`SystemHealthService.escape()`) has the identical shape as the CSV/Formula Injection bug just fixed in the Analytics export (`MetricsAggregatorService.escapeCsv()`) — it only escapes embedded quotes, no formula-trigger-character neutralization. It isn't currently exploitable because every value flowing into this specific export is server-computed (job names, service labels, health statuses, generated detail strings) with no free-text user input in the mix — but it's the same unguarded pattern, and would become a real issue if any future column ever surfaced user-controlled text.
- **A5 — Token Re-authentication: mechanism confirmed, but two specific claims are imprecise about *when* things actually happen.** The OAuth flow itself works as described and is genuinely audit-logged (`TOKEN_REAUTHORIZED`, via `TokenManagementService.handleCallback`). But: **"resumes suspended automated publishing" is not something the reauth action itself does** — `handleCallback` only updates the `FacebookPageToken` row (encrypts and stores the new token, clears the token's own validation-failure fields) and returns a success message that says "Automated publishing has resumed," but nothing in that method touches any already-blocked `Submission`. The actual resumption happens independently, up to 5 minutes later, when `TokenPublishingEscalationJob`'s own poll next checks `FacebookPublisherService.hasUsableActiveToken()` and finds it true, then retries the blocked submissions itself. Likewise, **"clears the associated token-expiry warnings (T-08, T-09)" doesn't happen in the reauth path either** — a submission's own `tokenBlockedAt`/`tokenEscalated24hAt`/`tokenFinalFailedAt` fields are only reset by `FacebookPublisherService.clearTokenSuspension()`, called exclusively from inside `markPublished`/`markFailed` when that specific submission's own retry actually resolves — an indirect, later, per-submission consequence, not a direct effect of the Administrator's Reauthorize click.

## Postcondition(s)

The actor views current, accurate infrastructure and operational health status, with real threshold-based warnings on storage, jobs, external services, and operational metrics alike. A missing/failed metric always renders as a distinct "unavailable" state rather than a false reading. Job history beyond the single latest run, and any per-institution storage breakdown, are not available despite the draft implying a drill-in exists for both.

## Not in the original draft at all

- **A manual "Re-run" trigger per background job** (`POST /system-health/jobs/{jobKey}/run`) — lets an Admin force any tracked job to run immediately instead of waiting for its schedule, audit-logged as `BACKGROUND_JOB_RUN`. A dedicated `/system-health/tokens/recheck` shortcut exists specifically for re-running `TokenHealthCheckJob`. **A real bug found and fixed the same day in this exact feature**: `ManualJobRunner.run()` used to run every job — including `PublishingSchedulerJob` and `TokenPublishingEscalationJob`, both of which call `FacebookPublisherService.publishMediaLinks` per submission with up to 3 retries and up to 125s of backoff sleep each — synchronously on the HTTP request thread. An Admin re-running either of those with several due/blocked submissions pending could trigger a multi-minute request; a client or gateway timeout would show a false failure while the job kept running to completion regardless, since nothing about the plain synchronous call was actually interrupted by the client giving up. Fixed by running exactly those two jobs on a background thread (`CompletableFuture.runAsync`, errors logged rather than propagated to a caller that already got its response) — every other job stays synchronous, since the response already reflecting the completed run is genuinely useful for the 13 fast, DB-only ones. The frontend mirrors the same two-job list to adjust its toast copy ("Started… — refresh to see its result" vs. "Ran…") since the response for the async pair no longer reflects the new run.
- The overall page-level rollup status (`SystemHealthSummaryDto.overall`) — worst-of across every storage/service/job/metric row, plus explicit counts of how many items are in each of `WARNING`/`UNHEALTHY`/`UNAVAILABLE`, surfaced as a single top-level indicator before an Admin even looks at individual sections.
- 11 of the 15 tracked background jobs aren't named anywhere in the draft (only "Publishing Scheduler, Stale Submission Detector, Embedding Reconciliation, Media Asset Retention Purge" are named explicitly, with a vague "and others").
- The precise 15-job "expected interval, flag stale only past 2× that interval" logic, and the separate, more lenient 23-hour "infrequent job" threshold that keeps a genuinely daily/weekly job from reading as `UNAVAILABLE` just because the app itself hasn't been running long enough to have completed its first run yet.

## Known limitations (not changed this pass)

- No job execution history and no per-institution storage breakdown exist despite the draft's main flow implying both are available via drill-in. Flagged during verification, not built, since both are genuine new features (a history table/endpoint; an institution-scoped storage query) rather than fixes to existing broken behavior.
- The System Health CSV export's `escape()` helper shares the same unhardened pattern as the Analytics export's formula-injection bug (now fixed there) — left as-is here since nothing user-controlled currently flows into this specific export, making it a hardening opportunity rather than an active vulnerability.
