# UC-2.4 Approval Workflow

**Use Case ID:** UC-2.4

**Use Case Name:** Approval Workflow

**Actor(s):** Moderator, Administrator — both are network-wide roles. `ValidationService`'s own class-level comment names this UC directly: "Returns the network-wide approval queue... Moderator and Admin accounts are both network-wide roles." Not institution-scoped for either role (see Main Flow step 2 correction).

**Precondition(s):** The actor is authenticated with an active session. At least one submission is in `pending` status in the Approval Queue for the flow to have something to act on — confirmed accurate, though the queue itself is defined as `pending ∪ in_review` (see step 1).

## Main Flow

1. The actor navigates to the Approval Queue, structured into **All, Pending, In Review, and Failed** tabs (`QueueFilter = "pending" | "in_review" | "all" | "failed"`) — matches the draft's four-tab claim exactly.
2. **Corrected:** the system displays submissions **network-wide**, not scoped to "the Moderator's assigned institution." `ValidationService.getQueue()` calls `submissionRepository.findValidationQueue()` with zero institution filtering — every Moderator sees every institution's queue, identically to Admin. Moderator became a network-wide, institutionless role project-wide on 2026-08-29; there is no per-institution queue view for either role.
3. The actor opens a submission and clicks Review. `ReviewLockService.acquire()` transitions `pending → in_review` and creates a `ReviewLock` scoped to that reviewer (**15-minute** TTL — `LOCK_DURATION_MINUTES = 15`, corrected 2026-09-24 from an earlier "60-minute" in this doc — renewed by a keep-alive ping while the panel is open).
4. The review screen shows a Facebook-style preview of the post (caption, media, watermark overlay toggle) beside a **Submission Details panel** — the single place for submission information (2026-09-24; see "Review screen layout" below). It leads with how and when the post publishes, then status, submitter, institution, event date, submission time, reviewers who edited it, and moderator notes, and ends with a **Review history** entry that opens the audit trail. **"Internal notes" is not a real field** — `Submission` has no such column; the closest matches are `description` (shown as "Moderator notes") and `validatorRemarks` (an *output* of Request Revision, not something pre-existing to show before review starts).
5. The actor reviews the content for completeness, accuracy, and appropriateness.
6. The actor may optionally edit allowed submission fields before taking a terminal action (A9/A10 below).
7. The actor then chooses Approve, Request Revision, or Reject.
8. Approve transitions the submission to `scheduled`, or publishes immediately for Live Event Fast-Track submissions (`FastTrackPublishingListener` reacting to `SubmissionApprovedEvent`) — confirmed accurate.
9. Request Revision transitions the submission to `needs_revision` and releases the slot reservation (`slotReservationService.release`) — confirmed accurate.
10. Reject transitions the submission to `rejected` and releases the slot reservation — confirmed accurate.
11. The system records actor identity, action, timestamp, remarks/edits/rejection notes in an immutable `ValidationLog` row (`ValidationAction`: `approved`, `edited`, `media_added`, `needs_revision`, `rejected`, `lock_acquired`, `lock_released`, `lock_expired`) — confirmed accurate, and more granular than the draft implies (media additions get their own distinct audit action, separate from a generic edit).

## Alternative Flows

- **A1 — No Submissions in Queue:** confirmed. Empty state reads "No submissions in this view."
- **A2 — Request Revision Without Valid Remarks:** confirmed. `validateRemarks()` enforces **10–1000 characters**, rejecting with `422` outside that range.
- **A3 — Concurrent Review Attempt:** confirmed. A second reviewer sees "This submission is currently being reviewed by Moderator {email}" and the panel renders read-only until the lock is released or expires.
- **A4 — Review Abandoned:** confirmed exactly. `ReviewLockCleanupJob` (every minute) and explicit `release()` both revert `in_review → pending` only if no terminal action was taken in that session.
- **A5 — Self-Submission Review — wrong as drafted, and its stale code comment is now fixed (2026-09-17).** The draft frames this as conditional ("allowed only if current governance permits it"). It is **unconditionally blocked**, with no governance toggle anywhere: `ReviewLockService.acquire()` throws `403` the instant `submission.getContributor().getId().equals(caller.userId())`, before a review can even begin — so the submitter can never even acquire the lock, let alone act. `ValidationService.approve()`'s own javadoc confirms this is deliberate and absolute: "Moderators cannot approve their own submissions; another moderator/admin must make the approval decision." `requestRevision()` and `reject()` previously carried a stale comment claiming "self-review is allowed but distinctly flagged in the audit log," inconsistent with `approve()`'s comment and with actual behavior — both now correctly document that self-review can never reach either method, since all three actions require holding a lock the submitter can never acquire.
- **A6 — Submission Approaching Publish Time Without Review:** confirmed real. `ValidationDeadlineNotificationJob` raises the approaching-deadline warning; `StaleSubmissionDetectorJob` (GR-T9) transitions an unreviewed submission whose scheduled time has passed to `missed_review`.
- **A7 — Media Assets Fail to Load: was not implemented, now is (2026-09-17).** There was no `onError` handling anywhere in the validation feature's frontend — a broken image just showed broken, with no distinct recovery affordance. `FacebookPostImage` now catches the load failure, shows a "This media asset failed to load" placeholder with a **Retry** button (re-requests via a cache-busting query param), and — since the reviewer was never actually blocked from acting even before this fix — Request Revision/Reject remain available the whole time underneath it, satisfying the draft's "proceed with available content" framing without a separate dedicated affordance for that specific phrase.
- **A8 — Failed Submission Handling:** confirmed accurate, and matches the Publishing Mode design documented in CLAUDE.md (2026-09-15): Admin can recover `publish_failed` submissions via manual publish/retry and can change publishing mode in either direction; a Moderator can also retry (same mode) or reschedule a non-Fast-Track item, but cannot change publishing mode or force Scheduled→Live — so "Moderators do not receive admin-only recovery controls" is accurate, though Moderators do have real (non-admin-only) recovery controls of their own, not zero capability here.
- **A9 — Edit Scope and Confirmation — overstated.** Edits are validated against media and schedule rules (guard rails, the 10-media-per-submission cap, A10 severity classification) before save. **"Watermark rules" validation does not exist** — the only watermark-related capability during review is the per-asset skip-watermark toggle itself, which is a setting, not a validation rule being checked.
- **A10 — Edit Audit Trail:** confirmed. `ValidationLog.editDiff` stores the before/after diff; edit severity (`QUIET` / `FLAGGED` / `ADDED_MEDIA`) is classified per the A10 governance tiers. **Bug fixed 2026-09-17:** the combined diff/severity used to scope to `logsSinceLock` — "everything since the most recent `lock_acquired` row." If a reviewer edited, then released or lost the lock (interrupted, 15-minute TTL expiry) before taking a terminal action, and later reacquired it to finish the review with no further edits, that reacquisition started a *new* `lock_acquired` row and silently dropped the earlier edit from the scan — the terminal action recorded `edited=false`, its diff omitted the earlier change, and the contributor was never told the submission had in fact been edited. `logsSinceLock` now scopes to the whole review cycle — since the last terminal action (approve/revise/reject), or the start of history if none — so an edit survives any number of lock releases/reacquisitions within the same cycle, while still correctly resetting after a real terminal action (e.g. a resubmission following Request Revision starts a clean cycle, as it should).
- **A11 — Contributor Notification of Edit — mechanism differs from the description.** The draft implies the edit indicator lives *inside* the approval notification. It's actually a **separate notification** (`submission_edited_in_review`, fired by `SubmissionEditedDuringReviewEvent`) delivered alongside the base approval notice, not a flag embedded within it. The base "approved and scheduled" notification/email never mentions edits at all on its own. The edit notification's wording varies by severity (`ADDED_MEDIA` / `FLAGGED` / `QUIET`), and only `FLAGGED`/`ADDED_MEDIA` trigger an email (not every edit).

- **A12 — Rejection Reasons (changed 2026-09-24).** Reject declines the post as submitted; the contributor sees the reason and can still edit and resubmit it. Its reasons are the ones that make the post unacceptable as it stands. Anything that only needs fixing (caption, photos, format) is a Request Revision case, and the dialog's "Only needs fixes?" line has a **Request Revision instead** shortcut that switches straight to the revision dialog. Accepted codes (`ValidationService.REJECTION_REASON_LABELS`, mirrored by `REJECTION_REASONS` in `frontend/src/lib/rejectionReason.ts`). The dialog shows each by name with a very short description (e.g. "Already posted or queued"); the table gives the fuller meaning:

  | Code | Label | When |
  |---|---|---|
  | `INAPPROPRIATE_CONTENT` | Inappropriate content | Offensive, misleading, or against DOST/DASIG guidelines |
  | `OUT_OF_SCOPE` | Not a DASIG activity | Unrelated to DASIG's programs or the network's mission |
  | `DUPLICATE_EVENT` | Duplicate | Already posted, or already in the queue |
  | `NO_LONGER_RELEVANT` | No longer timely | Posting it now would be outdated or misleading |
  | `RIGHTS_OR_PRIVACY` | Rights or privacy issue | Media used without permission, or people shown without consent |
  | `WRONG_INSTITUTION` | Belongs to another institution | The institution that ran the event should submit it |
  | `OTHER` | Other | Note required |

  `INCOMPLETE_CONTENT` and `WRONG_FORMAT` were removed: the backend now answers them with `422` ("…should be sent back with Request Revision"). Rejections already stored under those codes still display with their old labels. No reason is pre-selected, and Reject Submission stays disabled until one is picked (and, for Other, a note is written). The stored value is unchanged (`"CODE: note"`); only the contributor email switched to the readable label via `readableRejectionReason`. Covered by `ValidationRejectionReasonTest`.
- **A13 — Guided Walkthroughs (Guide button; rebuilt 2026-09-24).** Four view-only guides — queue, review, failed post, edit — built the same way as the composer's guide (UC-1.5): each step opens the part of the screen it describes and a click shield stops anything underneath from changing. The review guide opens the Submission Details panel and the Review History dialog, and shows the decision buttons (Approve / Request Revision / Reject / Edit / Unlock) as an inert preview with no lock taken (those buttons normally exist only while a lock is held). The edit guide switches between the Details, Media, and Schedule tabs. Whatever a guide opened is put back when it ends. Steps and per-step views: `frontend/src/features/onboarding/tours/validationTour.ts` (`VALIDATION_TOUR_VIEWS`).

- **A14 — Edit Safeguards: Review Before Save, Restore Original, Writing Check (added 2026-09-24).** Guards against edit accidents, mistakes, and abuse on top of A10's audit trail. None of it blocks a save, and the backend's rules for a valid edit are unchanged.
  - **Review before save.** The edit form's button is **Review & Save**: it opens "Review your changes" with every change side by side against the last saved version (title, event date, caption, publishing mode, publish slot, and a media summary: added / removed / reordered / caption or watermark settings changed). Each field except media has **Undo**. For a Live Event it warns that the post publishes the moment it's approved, so the contributor won't see the edit before it's live. With nothing changed, it says so and offers only Close.
  - **Restore original.** Beside the title, event date, and caption (and the publish slot, in the Schedule tab), **Restore original** appears once the field differs from what the contributor submitted. The contributor's value comes from the review history: the earliest `from` for that field among this review cycle's `edited` rows (`editSafeguards.contributorOriginals`), or the saved value if it hasn't been edited yet this cycle.
  - **Writing check (AI, advisory).** **Check writing** in the caption toolbar proofreads the current caption. When a Review & Save includes a caption change, the dialog checks the edit automatically against the contributor's original caption and reports only mistakes the edit introduced, plus any name, date, time, number, place, or claim it changed ("Meaning changed", which has no automatic fix). Each finding is applied or ignored individually. Nothing changes unless the reviewer applies it, and a failed check says so and still allows saving. The prompt leaves Filipino/Cebuano/Taglish, names, acronyms, hashtags, emoji, and decorative Unicode text alone. Endpoint: `POST /api/v1/ai/proofread` (`ProofreadController` → `ProofreadService`, Claude via `ClaudeVisionClient.generateText`), all three roles, 30 requests/hour/user (in-memory limiter, same as the caption tool). The server drops findings whose excerpt isn't in the text, no-op fixes, duplicates, and unknown kinds, and caps the list at 10 (`ProofreadServiceTest`). Recorded for AI Feature Adoption as `proofread` (`checked` + finding count, `applied` per fix; V104 — see UC-3.4). The same **Check writing** button is in the composer (UC-1.6).
  - **Admins see substantive edits.** A FLAGGED or ADDED_MEDIA review edit now also sends an in-app notification to every Administrator except the editor ("{editor} made substantive edits to '…'"). Before, only the contributor was told. `SubmissionEditedDuringReviewEvent` carries the editor (`editorId`); in-app only, since the contributor already gets the email (`NotificationEventListener.notifyAdminsOfSubstantiveEdit`).
  - **Fixed alongside:** the edit form's publish date came from the UTC date while its time was local, so a slot before 8 AM Manila time showed a day early in the form. Both now come from local time (`isoToLocalDateTime`).

- **A15 — Reviewing At or After the Publish Slot (added 2026-09-24).** Before, nothing checked the slot at approval time. Approving within ~5 minutes after the slot published late (the scheduler looks back 5 minutes). Approving around the 5-minute mark could be marked Publish Failed by the stale-slot sweep. After that, the sweep moved the post to `missed_review` even while a reviewer held its lock, so their decision then failed. Now:
  - **Warning.** For a Scheduled post under review, the review screen shows an amber "Publishes at 12:00 PM — N min left" banner from 30 minutes before the slot, and a red "The publish slot has passed" banner after it (30-second clock).
  - **The sweep doesn't take a locked item.** `SubmissionRepository.findMissedReviewSubmissions` skips a submission with an unexpired `ReviewLock`. If the lock expires or is released without a decision, it reverts to `pending` and the next sweep moves it to `missed_review` as before (A6).
  - **Approving after the slot is an explicit choice.** `ValidationService.approve` refuses a Scheduled post whose slot is now or earlier (`409`, "slot has already passed"). In the UI, Approve then opens "The publish slot has passed" with **Pick a new slot** (opens the edit form's Schedule tab; the normal guard rails and Review & Save apply, then approve). An Administrator also gets **Publish now** (`POST /validation/{id}/approve?publishNow=true`, `403` for a Moderator): the slot moves to now, the next scheduler run (within a minute) publishes it, and the late publish is audited as `LATE_PUBLISH_OVERRIDE`. `publishNow` with a future slot is `400`. Live Events are unaffected (no slot).
  - Request Revision and Reject still work after the slot; both release it.
  - The frontend no longer treats this `409` as "review lock expired". Tests: `ValidationServiceTest` (`approve_slotPassed_*`, `approve_publishNowWithAFutureSlot_isRejected`, `approve_futureSlot_approvesNormally`, `approve_liveEventWithAPastSlotField_isNotTreatedAsLate`).

## Review screen layout (2026-09-24)

Not in the draft; recorded because it changes where things are found.

- **One details surface.** The Facebook preview's "⋯" button used to open a separate "Submission History & Details" dialog that repeated the details panel's fields — confusing, and easy to mistake for Facebook's own post menu. The "⋯" is gone. The Submission Details panel holds every field, including status, event date, and moderator notes, which used to live only in the dialog. The dialog is now **Review History** (audit trail only), opened from the bottom of the panel with an action count. On desktop the panel can still be hidden and reopened with a "Details" button placed beside Guide (it used to float over Guide and cover it).
- **Edit form.** Titled "Edit submission", with Details / Media / Schedule as a segmented control. When a required field is empty (title, event date, caption, media — `editMissingFields`), a banner says exactly what's missing and those fields are marked. Before, Save was just disabled with no explanation. The caption shows a live count against the 3,000-character limit (UC-1.6). The Media tab adds from the library through two dialogs, **Add from Library** and **AI suggestions** (UC-1.7 matching, fetched only while that dialog is open; it used to render inline and overflow the form). The per-item **Media caption** dialog (≤500 chars, skip-watermark for images) has a counter, an explanation of each option, and a Done button. Changes still apply as you type.
- **Phones (≤860px).** The queue and the open submission are separate views. While a submission is open, the app's own top bar is hidden and a slim "‹ Queue" + guide row replaces it. The details panel is always shown below the preview.

## Postcondition(s)

- **On Approve:** submission is `scheduled` or published immediately (Fast-Track); slot confirmed (non-Fast-Track) or bypassed (Fast-Track); Contributor notified via the base approval notification, plus a separate edit notification if the session included edits; action and any edit diff recorded in `ValidationLog`. Confirmed accurate, modulo the "separate notification, not an indicator within it" correction above.
- **On Request Revision:** submission is `needs_revision`; slot released; Contributor notified with the moderator's remarks (in-app + email); action recorded. Confirmed accurate.
- **On Reject:** submission is `rejected`; slot released; Contributor notified with the reason's readable label + notes (in-app + email — the email used to show the raw code, fixed 2026-09-24). **Corrected 2026-09-24: rejection is not final.** `SubmissionService.submit` accepts `draft`, `needs_revision`, and `rejected`, and the contributor's view offers **Edit & Resubmit**. An earlier version of this doc said no resubmission was possible because `ValidationService` has no transition out of `rejected`, but that transition lives in `SubmissionService`. The difference from Request Revision is intent (declined as submitted vs. specific fixes requested), not finality — see A12.

- **Moderator scoping is wrong.** Not institution-scoped — network-wide, identical to Admin. See Main Flow step 2.
- **A5's self-review framing is wrong** (doc corrected; the stale `requestRevision`/`reject` comment that described it is fixed 2026-09-17). Not conditionally governed — unconditionally blocked at lock acquisition.
- **A7 (media-load-failure recovery) didn't exist — now does (fixed 2026-09-17).** See A7.
- **A9 overstates watermark validation.** No watermark *rule* is checked at edit time — only the skip-watermark toggle exists.
- **A11's mechanism is a separate notification, not an embedded indicator.**
- **Step 4's "internal notes" field doesn't exist** on `Submission`.
- **Rejection reason codes weren't in the draft** — now documented, and narrowed on 2026-09-24, in A12.
- **Step 3's lock TTL was wrong in this doc** ("60-minute"); the code has always used 15 minutes.
- **Real bug found and fixed (2026-09-17), not in the original draft's scope:** the cross-lock-session edit-diff drop described in A10 above.
