# UC-3.2 Automated Facebook Post Publishing

**Use Case ID:** UC-3.2

**Use Case Name:** Automated Facebook Post Publishing

**Actor(s):** System.

**Precondition(s):** At least one submission is `scheduled` with a slot that has arrived, or a Fast-Track submission has just been approved (UC-2.4).

## Main Flow

1. `PublishingSchedulerJob` runs every minute (`@Scheduled(cron = "0 * * * * *")`), querying `scheduled`/`direct_post_scheduled` submissions whose slot falls within a 5-minute lookback window (accounting for cron/server lag). A Fast-Track submission bypasses this query entirely — see A5.
2. Each due submission is **claimed before any Graph API call** — `PublishingQueryService.claimForPublishing` runs an atomic conditional `UPDATE` (`scheduled → publishing` / `direct_post_scheduled → direct_post_publishing`); a submission another scheduler pass (or app instance) already claimed returns 0 rows and is skipped. **This is the actual double-publish safeguard, and it wasn't mentioned in the original draft at all** — nothing else in the flow prevents two overlapping scheduler runs from both trying to publish the same post.
3. The system fetches and decrypts the active `FacebookPageToken`. If expired, see A3.
4. Media is inspected: image-only → 2-step photo path (step 5); video-only → single-call path (step 6); mixed image+video → immediately `markFailed`, no retries attempted (see A6 note below — not really an "alternative flow," it's a first-attempt hard stop).
5. **Photo publishing (2-step)**: every image is first staged unpublished (`POST /{page}/photos`, `published=false`) — including that image's own per-asset caption on the individual staging call when one was set during drafting (`SubmissionMediaAsset.caption`, confirmed threaded through `mediaCaptions`/`stagePhoto`). Watermarking happens immediately before staging, resolved fresh at this exact moment (`WatermarkApplicationService.resolvePublishUrl`) — see the note on watermark timing below. Once every photo is staged, a single `POST /{page}/feed` call attaches every staged photo id and publishes with the submission's own main caption.
6. **Video publishing (single call)**: one `POST /{page}/videos` per attempt (`file_url` + `description` + `published=true`) — no staging, no separate feed call.
7. On success: status becomes `published` (or `admin_direct_post` for a direct post), `platformPostId`/`publishedAt` are recorded, `PostPublishedEvent` fires (Contributor notification, `submission_published` — draft's "T-04"), and the calendar card turns green.
8. On failure: up to 3 attempts with backoff (5s, 25s, 125s). Exhausting all 3 marks the submission `publish_failed` (or `direct_post_failed`), fires `PublishFailedEvent` (Administrator notification, `submission_publish_failed` — draft's "T-06"), and the calendar card turns red; the submission becomes recoverable from the Review Queue's Failed tab (UC-2.4 A8, UC-3.4).
9. A separate job, `StaleSubmissionDetectorJob` (`@Scheduled(cron = "0 */5 * * * *")`, every 5 minutes), performs two distinct sweeps that the original draft collapsed into one — see A2 below, since this is the single biggest correction to the draft.

## Alternative Flows

- **A1 — Feed Post Failure After Partial Photo Staging: corrected, the cleanup-failure handling described in the draft doesn't exist.** If staging succeeded for one or more photos but the final feed-post call then fails after all retries, `cleanupStagedPhotos` does attempt to `DELETE` each staged photo — confirmed. But **the draft's claim that a failed deletion produces "a consolidated notification listing the unresolved IDs with a link to the Facebook Media Manager" is invented; no such thing exists anywhere in the codebase** (grepped for "Media Manager" — zero hits). A failed or exceptioning deletion call is only ever `log.warn`'d server-side — nothing is escalated to the Administrator beyond the normal, generic `PublishFailedEvent`/"T-06" notification that fires regardless of whether cleanup succeeded. The *originally staged* photo IDs for that attempt (not specifically the ones cleanup failed on) are recorded in `PublicationAttempt.photoIdsStaged`, a real, queryable column — but it's never surfaced anywhere in the admin Resolution Center UI (`FailedPublicationDto` doesn't expose it). Net effect: an admin who needs to manually clean up a leftover Facebook photo after a cleanup failure has no in-app way to find its ID; they'd need direct database access to `publication_attempts`.
- **A2 — Missed Slot Detection: the draft's single "missed-window → PUBLISH_FAILED" flow is actually two distinct sweeps with two distinct outcomes.** `StaleSubmissionDetectorJob` runs both, every 5 minutes, but they are genuinely different:
  - **Already-approved submissions whose scheduler pass never ran** (`findAndMarkFailed`): a `scheduled`/`direct_post_scheduled`/`direct_post_publishing` submission whose slot passed more than 5 minutes ago without ever being picked up (e.g. the app was down) — these transition to `publish_failed`/`direct_post_failed`, exactly as the draft describes, firing `PublishFailedEvent` ("T-06").
  - **Never-reviewed submissions whose slot simply passed** (`findAndMarkMissedReview`): a `pending`/`in_review` submission — never approved at all — whose scheduled time arrived and passed while still awaiting review. These transition to a **separate status, `missed_review`**, not `publish_failed`. The slot reservation is released, and a distinct, uncoded event fires (`SubmissionMissedReviewEvent`, referenced only as "UC-2.4 A6" in code comments, not given its own T-number). Recovery for this case doesn't go through the Failed tab's manual-publish flow at all — "Retry with New Schedule" sends it back to `pending`, **re-entering the Approval Workflow** from scratch, since it was never actually approved in the first place. The calendar renders `missed_review` with its own distinct amber color, separate from both `published` (green) and `publish_failed` (red).
  
  The draft's step 2 treats "missed the scheduled time" as one outcome; in reality, *which* status a submission reaches depends entirely on whether it was ever approved before its slot passed.
- **A3 — API Token Expiry: draft's T-08 numbering only covers the initial warning, not the 24h/48h escalation.** Confirmed accurate that an expired token blocks publishing without consuming a retry attempt, and that there's a 24h/48h escalation sequence culminating in `publish_failed` if not reauthorized. But in code, `token_expiring` ("T-08") is only the advance pre-expiry warning (`TokenExpiryWarningEvent`, a days-until-expiry countdown) — a genuinely different, earlier notification than the 24h/48h escalation. The escalation sequence itself (`TokenPublishingSuspendedEvent`, staged `FIRST_ALERT` → `ESCALATION_24H` → `FINAL_FAILURE`) reuses the `token_invalid` notification type (the same one used for a hard token-validation failure elsewhere) and has no T-number of its own in the code comments. The final-failure message text does confirm the draft's outcome is correct — "...blocked... for 48 hours and was moved to Publish Failed for manual recovery."
- **A4 — Development Mode Visibility.** Confirmed correctly out of DASIGConnect's own scope — this is purely a Meta/Facebook platform-level fact (App Review/Development Mode, configured on developers.facebook.com), documented as a note in `README.md` with zero corresponding flag, env var, or conditional anywhere in the codebase. Nothing to fix; the draft's framing as "expected behavior, not a system error" is accurate.
- **A5 — Live Event Fast-Track Immediate Publish: mechanism corrected — this is an async event listener, not an inline synchronous call.** `ValidationService.approve()` does not publish anything itself; it only fires `SubmissionApprovedEvent`. A separate class, `FastTrackPublishingListener`, listens via `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)` (so it only runs once the approval transaction has actually committed) combined with `@Transactional(propagation = Propagation.REQUIRES_NEW)` for its own publish attempt — it checks `submission.isFastTrack()`, claims the submission the same atomic way the scheduler does, and calls `FacebookPublisherService.publishMediaLinks` directly. This deliberately bypasses `PublishingSchedulerJob`'s cron entirely, since that job's query requires a non-null `scheduledAt`, which a Fast-Track submission never has.
- **A6 — Mixed-Media Submission.** Confirmed accurate — detected immediately, routed straight to `publish_failed` with the Administrator alerted, no retries attempted at all (not even the standard 3-attempt sequence).
- **A7 — Fast-Track's Transaction Boundary Violated the Scheduler's Own Documented Rule (found and fixed 2026-09-18, not in the original draft).** `PublishingSchedulerJob` is explicit — its class comment states *"The Facebook API call happens outside any transaction to respect the HikariCP 5-connection limit,"* matching `FacebookPublisherService`'s own header comment that it *"must NEVER be called while holding an open DB transaction."* `FastTrackPublishingListener` didn't follow this: both `onSubmissionApproved`/`onFastTrackRetry` carried `@Transactional(propagation = REQUIRES_NEW)` spanning the entire method — the claim, loading media, **and** the live Graph API call, including up to 3 retries with cumulative backoff sleeps of 5s + 25s + 125s (155 seconds, before network latency). Given the project's deliberately tiny 5-connection Supabase pool, this was a real resource-exhaustion risk: a slow or retrying Fast-Track publish could hold a connection for minutes, starving every other request in the app. Fixed by removing the `@Transactional` annotation from both listener methods entirely — `PublishingQueryService`'s `claimForPublishing`/`loadMediaLinksForSubmission` calls still get their own short, separately-committed transactions via the Spring proxy (a different bean, so no self-invocation issue), and `publishMediaLinks` now runs with no transaction open, exactly mirroring the scheduler.
- **A8 — A Fast-Track Submission Stuck Mid-Publish Had No Recovery Path (found and fixed 2026-09-18, not in the original draft).** If a Fast-Track submission was claimed (`publishing`) and the app crashed or restarted before `markPublished`/`markFailed` ran, nothing would ever recover it. `StaleSubmissionDetectorJob`'s existing stuck-`publishing` sweep (`findMissedScheduledSubmissions`) does cover a stuck **Scheduled** submission — its query does include `publishing`/`direct_post_publishing` statuses, contrary to what its own class-comment implies — but it requires `scheduledAt < cutoff`, and a Fast-Track submission's `scheduledAt` is always `null`, so it could never match. Fixed in two parts: `SubmissionRepository.claimForPublishing`'s atomic claim now also bumps `updatedAt` (a bulk JPQL `UPDATE` bypasses the entity's `@PreUpdate` lifecycle callback, so this had to be done explicitly), and a new `findStuckFastTrackPublishing` query catches `publishing`/`direct_post_publishing` submissions with `scheduledAt IS NULL` whose `updatedAt` is older than the same 5-minute cutoff — comfortably longer than the ~155-second worst-case legitimate in-flight duration, so a genuinely still-running publish is never falsely flagged. A token-expiry block is excluded the same way the existing sweep excludes it (that case reverts to `scheduled`/`direct_post_scheduled`, not left in `publishing`, and is handled independently by `TokenPublishingEscalationJob` regardless of `scheduledAt`).

## Postcondition(s)

On success, the submission is `published` with the platform post ID recorded, the Contributor notified (`submission_published`), and the calendar card green. Analytics reflects the publication within, in practice, **at most 60 seconds — but because of a real, fixed 60-second in-memory cache TTL on the summary endpoint (`MetricsAggregatorService.summary`, `@Cacheable` on `analyticsSummary`, no eviction tied to `PostPublishedEvent`), not because reads are live** — worst case a viewer sees pre-publish numbers for up to just under 60 seconds; best case (cache miss) it's instant. The `/export` and `/report` endpoints are not cached at all. **Correction (2026-09-18): the draft's "≥95% of scheduled publications within ±5 minutes" claim is NOT aspirational — it was already implemented, just under a different name.** An earlier verification pass of this doc grepped for "accuracy"/"95%"/"SLA" and found nothing, and wrongly concluded the metric didn't exist. It does: `AnalyticsRepository.operationalHealth()` already counts published submissions where `ABS(EXTRACT(EPOCH FROM (published_at - scheduled_at))) <= 300` — exactly the ±5-minute window — and surfaces the rate to Administrators on the Analytics dashboard as "On-Time Publication" (`OperationalHealthPanel.tsx`). What was genuinely missing was the 95% target comparison itself (the rate was shown, but never checked against a threshold, unlike "Content Completeness" on the same dashboard, which already had one). Fixed by adding `ON_TIME_PUBLICATION_TARGET = 95.0` and a `meetsOnTimePublicationTarget` flag to `OperationalHealthDto`, mirroring `COMPLETENESS_TARGET`'s existing pattern, and a target badge ("On target"/"Below target") in `OperationalHealthPanel`. Kept admin-only, matching where this metric already lived — not promoted into the top-level KPI tiles everyone sees, since that would have changed its audience beyond what existed. Submissions whose slot is missed are detected within 5 minutes by `StaleSubmissionDetectorJob`, but land in one of two different terminal states (`publish_failed` or `missed_review`) depending on whether they'd already been approved — see A2. Token expiry suspends publishing with escalating alerts at 24 and 48 hours, though only the initial warning carries the draft's cited "T-08" label in code.

## Not in the original draft at all

- The atomic claim-before-publish step (`PublishingQueryService.claimForPublishing`) — the actual mechanism preventing a double-post from two overlapping scheduler runs, entirely unmentioned in the draft's flow.
- The `missed_review` status as something genuinely distinct from `publish_failed`, with its own recovery path (back into the Approval Workflow, not manual publish) and its own calendar color.
- `PublicationAttempt.photoIdsStaged`, the real (if under-surfaced) record of staged photo IDs for a failed publish attempt.
- The `TokenExpiryWarningEvent`/`token_expiring` vs. `TokenPublishingSuspendedEvent`/`token_invalid` distinction — two different event types feeding what the draft describes as one continuous "T-08" alert sequence.
- The role-based calendar masking that neutralizes a non-owning Contributor's view of another submission's private workflow status (`pending`/`in_review`/`needs_revision`/`rejected`/`direct_post_scheduled`) to a generic "scheduled" color, unrelated to this use case's publishing mechanics but implemented in the same `calendarStatus.ts` file.

## Fixed after initial verification (2026-09-18)

- **A1's silent cleanup failure is fixed.** `cleanupStagedPhotos` now returns the subset of staged photo IDs it couldn't delete; `PublicationAttempt.photoIdsCleanupFailed` (V97 migration) records that subset separately from the full staged list, `FailedPublicationDto.unresolvedPhotoIds` exposes it, and the Review Queue's Failed tab (`ValidationQueueScreen` — Resolution Center's functionality now lives there, not a separate screen) shows it as a copyable list when present. There's still no direct link into a Facebook Media Manager (that never existed, draft or otherwise) — an admin still has to paste the IDs into Facebook's own tools manually — but the IDs are no longer buried in a server log only.
- **The ±5-minute/95% publish-accuracy postcondition is fixed** (see the correction note under Postcondition(s) above) — it wasn't actually missing, just missing its target comparison, now added to `OperationalHealthDto`/`OperationalHealthPanel`.
- **A7 (Fast-Track's transaction boundary) and A8 (a stuck Fast-Track publish's missing recovery path) are fixed** — see the Alternative Flows above for full detail. Neither was in the original draft; both were found investigating the publishing pipeline's real internals, not from any discrepancy against the SRS text itself.

## Known limitations (not changed this pass)

- The 24h/48h token-expiry escalation notifications have no distinct T-code of their own in the codebase, reusing `token_invalid`'s notification type. Cosmetic/documentation-only gap, not a functional one — left as-is.
