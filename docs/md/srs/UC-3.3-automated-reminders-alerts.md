# UC-3.3 Automated Reminders & Alerts

**Use Case ID:** UC-3.3

**Use Case Name:** Automated Reminders & Alerts (the notification system: triggers, delivery channels, in-app badge/history, and the AI Content Idea Suggestions tied to the Empty Schedule Warning).

**Actor(s):** System, Contributor, Administrator — **and Moderator, missing from the draft's actor list.** Moderators are recipients of most triggers (T-01, T-06, T-07, T-11 among others) and are explicitly eligible for Messenger linking alongside Administrators (see A4).

**Precondition(s):** A triggering event has occurred (submission state change, publishing outcome, token health change, or empty-schedule condition).

## Main Flow

1. The system detects a triggering event. **The draft's "T-01 through T-12" is real, code-documented numbering** — not invented for the SRS — found in doc-comments throughout `NotificationEventListener` and in the frontend's `EVENT_META` display table. But it's **incomplete**: roughly a dozen more real trigger events exist untagged in that scheme, several just as significant — `submission_needs_revision` (Revision Requested), `submission_edited_in_review` (edit-during-review, severity-gated), `submission_missed_review` (UC-2.4 A6), `watermark_apply_failed` (UC-2.5 A4), a separate token-suspension escalation sequence (`FIRST_ALERT`/`ESCALATION_24H`/`FINAL_FAILURE`, distinct from T-08's pre-expiry warning), `institution_no_moderator`, `institution_onboarded`, `user_role_changed` (tagged "T18" in one stray comment, inconsistent with the T-01..T-12 scheme), `admin_promotion_requested`, `admin_promotion_declined`. `NotificationEventType` has 29 values total.
2. The system determines recipient(s) and channel(s) per trigger — confirmed real, per-call-site configuration (see the channel matrix under A4 below), not uniform across all triggers.
3. Dispatch via in-app (always, gated only by the recipient's `notifyInApp` preference), and/or email, and/or Messenger as configured for that trigger.
4. **The in-app badge updates in real time everywhere — fixed 2026-09-18, previously only on the Notifications screen itself.** `NotificationService` implements genuine SSE push (`SseEmitter`, `/api/v1/notifications/stream`) and dispatches synchronously right after each DB write — a saved notification reaches an open SSE connection essentially instantly. That connection used to be opened only by the full `useNotifications(user)` hook, used exclusively inside `NotificationsScreen.tsx` — the persistent navbar bell badge (`DashboardLayout.tsx`) used a separate, lighter hook with no SSE subscription at all, polling every 3 minutes instead. Fixed by having `useNotificationUnreadCount` open its own SSE connection too, reacting to `notification`/`read`/`read-all` events by re-fetching the authoritative unread count from the server (`GET /notifications/unread-count`) rather than doing local arithmetic — deliberately, since this hook and `useNotifications` can both be mounted at once (navbar + Notifications screen open together), each with its own independent SSE connection, so the same server event reaches the tab twice; a naive increment/decrement would double-count, but re-asking the server for the true number is safe no matter how many times it fires. The 3-minute poll stays as a safety net for a dropped stream the reconnect loop hasn't caught up with yet, not the primary update path anymore.
5. Clicking a notification navigates to the relevant screen — confirmed working (`NotificationsScreen.tsx`'s `handleRowClick`, using a server-set `deepLink` per trigger, plus special-casing for owner-facing events to route to "My Submissions").
6. Full notification history with read/unread state — confirmed (`GET /api/v1/notifications/history`, paginated, role-scoped filters, day-grouping).

## Alternative Flows

- **A1 — Email Delivery Failure.** Not independently re-verified this pass (email retry policy is `EmailDeliveryService`'s own concern, out of scope for this specific look); in-app delivery is confirmed unconditional and independent of email outcome — every `createNotification` call writes the row and dispatches SSE regardless of whether the same call site also attempts email.
- **A2 — Notification Read-State Sync Across Sessions: fixed 2026-09-18.** Previously not implemented at all: `markRead`/`markAllRead` only wrote to the database, with no push to other open SSE connections of the same user — a second tab/device only learned of a read via its own next 3-minute poll. Fixed by adding `NotificationService.dispatchRead`/`dispatchReadAll`, called right after the DB write, pushing a `read` (with the notification id) or `read-all` SSE event to every live emitter for that recipient — not just the one that originated the action. The frontend (`useNotifications`) now handles these via `applyRemoteRead`/`applyRemoteReadAll`, updating the local cache the same way a locally-initiated mark-read does, just without re-calling the API. The self-echo case (the originating tab also receives its own read event back) is naturally idempotent — by the time it arrives, the optimistic local update already happened, so the `wasUnread` check is already false and no double-decrement occurs. Still worth noting: the draft's example ("clicking the linked submission directly" marks it read) has no actual second entry point in the code — `markNotificationRead` is only ever called from within the notifications feature itself, nowhere else; this fix syncs *existing* read actions across sessions, it doesn't add a new way to trigger one.
- **A3 — High-Volume Notification Batching: aspirational, no general implementation exists.** Grepped the whole notification pipeline for batch/throttle/dedupe/coalesce logic tied to bursts of the same trigger type — nothing. The only digest-shaped feature anywhere in the system is a fixed **weekly** summary of one specific event class (failed media embeddings, `EmbeddingFailureDigestJob`) — not a general consolidation mechanism applicable to any trigger, and not triggered by volume at all (it's purely time-based).
- **A4 — Facebook Messenger Delivery: channel matrix confirmed exact; eligibility claim needs correcting.** The draft's claim that only T-01, T-06, T-11 get Messenger delivery is **precisely correct** — exactly 3 call sites in the whole codebase send via Messenger, matching those three triggers exactly. But the draft's framing of the recipient as "the Administrator's linked personal Facebook account" is wrong: `MessengerConnectionService.createLinkCode()` explicitly allows **Moderator or Admin** (`"moderator".equals(user.role()) || "admin".equals(user.role())`, 403 otherwise) — matching UC-1.4's Messenger-linking note, not Admin-only. The full channel matrix beyond Messenger, for reference: email additionally goes out on `submission_approved`, `submission_rejected`, `submission_needs_revision`, `submission_edited_in_review` (severity-gated), `submission_publish_failed`, `submission_missed_review`, `token_expiring`, `token_invalid` (both the T-09 handler and the untagged suspension escalation), `watermark_apply_failed`, `fast_track_submission`, `institution_no_moderator`, `admin_promotion_requested` — everything else (T-02 duplicate `submission_scheduled`, T-04/T-05 published events, T-07, T-10, T-12, `institution_onboarded`, `user_role_changed`, `admin_promotion_declined`) is in-app only.
- **A5 — Messenger Not Linked: confirmed accurate.** `MessengerDeliveryService.sendToUser()` looks up a linked PSID; absent, it returns `false` silently — no exception, no interruption to the rest of the dispatch. Any HTTP/config failure on the Messenger send itself also fails soft (logs a warning, returns `false`). Matches the draft's "silently skip" exactly.
- **A6 — Content Idea Suggestions: mostly real and correctly implemented, with one real mechanism discrepancy.** `ContentIdeaSuggestionService.generateSuggestions(Institution)` is genuinely wired to T-07 exclusively — `EmptyScheduleWarningJob` (weekly cron, `0 0 8 * * MON` by default) is the *only* thing that ever calls it; there is no REST endpoint and no on-demand composer UI path to it at all. It blends two signals and calls Claude (`ClaudeVisionClient.generateText`) to synthesize 2-3 plain-language bullet suggestions from them, capped at 3. **The cross-institution signal matches the draft well** (categories other institutions posted in the last 60 days). **The "historical/seasonal" signal does not match the draft at all**: the draft describes matching this institution's own posting history from the same calendar period in prior years, sourced via the Facebook Graph API. The actual implementation (`SubmissionRepository.findRecentAndHistoricalPostTitles`) is simply the 10 most recently published event titles from the local database, ordered by creation date — no calendar-period alignment logic of any kind, and no Facebook Graph API call anywhere in this path. This is a genuine correction needed in the SRS, not just an imprecision.
- **A6a — Insufficient Historical Data: confirmed accurate.** `generateSuggestions` returns an empty list outright when both signals are empty, rather than fabricating anything — covered by its own test.
- **A6b — Suggestions Are Advisory Only: mostly confirmed, one nuance.** No draft is ever created or pre-filled — the service only returns `List<String>`, never touches submission creation. But the draft's "Contributor not notified automatically" isn't quite right as stated: `NotificationEventListener.onEmptySchedule()` embeds the suggestions directly into the same `empty_schedule_warning` notification sent to moderators, admins, **and that institution's own Contributors** — so Contributors do receive the suggestions, inlined into the standard T-07 broadcast everyone else gets. There's no *separate*, suggestion-specific notification to Contributors, but they aren't excluded from seeing them either.

## Postcondition(s)

Every configured recipient of a triggering event receives it via all channels actually configured for that trigger (in-app always; email and/or Messenger only where the code specifically wires them, not uniformly), recorded with accurate read/unread state in their history. The in-app badge reflects this within seconds everywhere in the app, not only on the Notifications screen (fixed 2026-09-18). Read state now propagates across a user's simultaneous sessions/tabs within seconds too (fixed the same day) — previously it did not. A weekly empty-schedule scan (0 scheduled posts in an institution's next 7 days) is the sole source of T-07, optionally accompanied by AI-generated content suggestions blending a recency signal (not a true seasonal one) and a cross-institution signal, always advisory and never auto-drafted.

## Not in the original draft at all

- 17 of 29 `NotificationEventType` values have no T-number in the draft's scheme at all, several covering meaningfully important events (missed review, revision requested, watermark failure, the 24h/48h token-suspension escalation distinct from the pre-expiry T-08 warning).
- The SSE (`Server-Sent Events`) push mechanism itself, and how it's now used for two purposes beyond delivering new notifications: cross-session read-state sync and a live-updating navbar badge (both added 2026-09-18).
- The role-scoped notification filter sets in `NotificationsScreen` (`CONTRIBUTOR_FILTERS`/`MODERATOR_FILTERS`/`ADMIN_FILTERS`) and day-grouped history layout.
- `EmbeddingFailureDigestJob`'s weekly digest (T-12) — the system's one real, narrow example of anything resembling "batching," despite it being time-based rather than volume-triggered and specific to one event class.

## Fixed after initial verification (2026-09-18)

- **A2 (cross-session read-state sync) is fixed** — see the corrected Alternative Flow above. `NotificationService.dispatchRead`/`dispatchReadAll` push to every live emitter for a recipient, not just the originating one; the frontend applies these the same way a local mark-read updates its cache.
- **The navbar badge's up-to-3-minute lag is fixed** — see the corrected Main Flow step 4 above. `useNotificationUnreadCount` now has its own SSE subscription, refetching the authoritative count on push rather than polling as the primary path.

## Known limitations (not changed this pass)

- A3 (high-volume batching) remains a real gap against the draft with no corresponding implementation — the draft itself hedges this as "at system discretion," so it isn't a violated requirement, but nothing resembling general consolidation logic exists. Would need a genuine windowing/consolidation design, not a one-line fix; left as-is since it wasn't requested.
- The Content Idea Suggestions "historical" signal being recency-based rather than truly seasonal (no calendar-period matching, no Graph API call) is a mechanism gap, not a bug — the feature works as designed, just not as the draft describes its internals. Left as-is; a genuine seasonal-matching redesign would be a larger scope decision.
