# UC-3.4 Social Engagement Analytics

**Use Case ID:** UC-3.4

**Use Case Name:** Social Engagement Analytics (the Analytics dashboard).

**Actor(s):** Contributor, Moderator, Administrator — **the draft omits Moderator entirely from its actor list, then explicitly excludes Moderator in A5. Both are wrong.** `AnalyticsController` is `@PreAuthorize("isAuthenticated()")` only, with no role restriction; the frontend's `/analytics` route explicitly allows all three roles (`allowedRoles={["admin", "moderator", "contributor"]}`), and the sidebar nav item is unconditionally `visible: true`. A Moderator gets a full, network-wide analytics view — confirmed to be an even fuller access level than a Contributor's, not a blocked one.

**Precondition(s):** The actor is authenticated with an active session. At least one submission has been published (UC-3.2) to generate analytics data.

## Main Flow

1. The actor navigates to Analytics from their sidebar — confirmed, unconditionally visible to all three roles.
2. Role-scoped metrics: **the draft's role breakdown is wrong on two of three roles.**
   - **Contributor**: draft says "their own institution where enabled" and (implicitly, since it's not restated) their own submissions. Neither is accurate. There is no "enabled" toggle anywhere in the code — Analytics is unconditionally available. And scope is **institution-wide, not per-Contributor**: `MetricsAggregatorService.scopeFor()` builds an `AnalyticsScope` that does carry the Contributor's `userId`, but that field is never referenced in any SQL query in `AnalyticsRepository` — every query filters purely on `institution_id`. A Contributor's `contributorAnalytics` numbers (submitted/published/revision counts) include every submission at their institution, not just their own.
   - **Administrator**: confirmed accurate — network-wide, with an institution filter, date range, and drilldown views (Validator/Review Workload, Contributor Breakdown) that appear only once a specific institution is selected.
   - **Moderator**: **the draft's claim that Moderators don't see the Analytics nav item and can't access it by URL or API is flatly false.** `scopeFor()` has an explicit `"moderator"` branch granting network-wide scope (the same `postsByInstitution`/engagement data Admin sees), with one restriction: a Moderator is explicitly forbidden from applying the institution filter (`403` if attempted) — they always see the whole network, unfiltered, never drilled down to one institution. The real split isn't "Moderator blocked, others allowed" — it's **per-metric**: exactly two export/report metrics, `operational-health` and `ai-performance`, are Admin-only; every other metric (`posting-delay`, `content-completeness`, `posts-by-institution`, `facebook-engagement`) is available to Moderator and Contributor too. This is likely the actual source of the draft's confusion — a real, narrow "Moderator/Contributor blocked from two specific metrics" fact got generalized into "Moderator blocked from Analytics entirely."
3. Filters: institution (Admin only, backend-enforced — a Contributor gets a hard `403` if they even attempt to pass an `institutionId`, not merely a frontend that never offers the option), date range (4 fixed options: `7d`/`30d`/`90d`/`ytd`, not a free picker), and — **category filter does not exist.** `AnalyticsRepository`'s own code comment states plainly: "Category filtering was removed — submissions carry no category." `Submission.category` exists as a field but is unused anywhere in Analytics. The draft's category filter is aspirational.
4. Export/report: **"formatted report" is not a separate document.** `GET /export/{metric}` is a genuine CSV download. `GET /report/{metric}` is a paginated JSON endpoint rendered as an in-app modal (`FullReportModal`) with a daily-breakdown tab and a detail-rows tab — explicitly the same underlying rows as the CSV, per the modal's own UI copy, not a distinct generated document (no PDF, no separately formatted artifact).
5. **Auto-refresh interval: the draft's "every 60 seconds" is wrong — it's every 5 minutes.** There genuinely is a frontend auto-refetch (`BACKGROUND_REFRESH_MS = 5 * 60_000`, only while the tab is visible), plus a manual Refresh button. The 60-second number that does exist in the codebase is unrelated to UI refresh — it's the backend's server-side cache TTL (`MetricsAggregatorService.summary` is `@Cacheable`, 60s, no eviction tied to any event) and a matching React Query `staleTime`, both of which govern whether a *request* gets cached data, not whether the dashboard *automatically re-requests*. The draft conflates these two different 60-second numbers into one incorrect claim about the actual refresh cadence.

## Alternative Flows

- **A1 — Insufficient Data: confirmed accurate.** Genuine per-panel empty states throughout (engagement panel, posts-by-institution chart, status donut, the report modal's daily/detail tabs, KPI tiles showing a "No data" pill) — none of these render raw errors for an empty dataset.
- **A2 — Facebook Engagement Data Delayed: confirmed accurate.** `FacebookEngagementSummaryDto.pendingCount` is a real, visible indicator ("N posts pending updated figures from Facebook"), shown in both Contributor and Admin/Moderator views, not merely computed and dropped.
- **A3 — Export Failure: confirmed wrong.** `FullReportModal`'s CSV download handler has no `catch` block, only `finally` — a failed export silently reverts the button from "Preparing Export…" back to normal with no error message and no retry affordance; the failure becomes an unhandled promise rejection in the console. (The **report** modal's own JSON fetch, a separate code path, does have genuine inline error + retry UI — but that's for loading the report view, not for the CSV export button specifically, which is what A3 describes.)
- **A4 — Cross-Institution Access Attempt: confirmed accurate, and stronger than the draft implies.** This isn't just the frontend never offering another institution's data — the backend independently enforces it: a Contributor's institution always comes from their own JWT, never from a client-supplied parameter, and passing any `institutionId` at all as a Contributor gets an unconditional `403`, regardless of what value was sent.
- **A5 — Moderator Access Attempt: flatly false, see Main Flow step 2.** No rejection of any kind exists for a Moderator accessing Analytics — nav item, route, and every summary/most export endpoints are all open to them, with only the two admin-only metrics and the institution-filter restriction actually gating anything for that role.

## Postcondition(s)

Every actor sees accurate, role-scoped analytics: Contributor and Moderator both get real data (institution-wide and network-wide respectively, not blocked or toggled), Admin gets full network-wide data with drilldown. Filtering and export work as described, except export failures are currently silent rather than surfaced with a retry option, and there's no category filter to apply regardless of role. The dashboard refreshes automatically, but on a 5-minute cadence, not 60 seconds.

## Not in the original draft at all

- **AI Feature Adoption panel** (Admin-only): caption acceptance rate, tag correction rate, media recommendation relevance rate, with an explicit "insufficient data" flag below 20 events — a genuinely different metric family from anything the draft's terse "role-scoped metrics" phrase captures.
- **Page Performance card** (Admin-only): live Facebook Page-level insights (reach, engagements, new follows, views) fetched directly from the Graph API per dashboard load, distinct from per-post engagement — explicitly designed to degrade gracefully (returns `null`, dashboard still renders) on any Facebook API failure or outage.
- **Validator/Review Workload panel and Contributor Breakdown table** — both Admin-only, and both gated specifically on having drilled down to one institution (submission volume, pending/in-review counts, average turnaround, queue-aging risk; individual contributor stats within that institution). Not available to Moderator at all, since Moderators can never select a single institution to drill into.
- **A hardcoded placeholder panel for non-admin roles**, worth flagging directly to whoever maintains the SRS: the "Content Quality & Compliance" panel a Contributor or Moderator sees (`OperationsAndEngagementCard`, when the admin-only `operationalHealth` block is null) shows **"Content Completeness 100%", "Watermark Valid 100%", "Publish Readiness: Optimal"** as literal hardcoded strings, not derived from real data — only "Missing Metadata" in that same panel is a genuine computed number. A Contributor or Moderator reading this panel could reasonably believe these are live metrics; they are not.
- The ±5-minute publish-accuracy window referenced inside the on-time-publication SQL ties directly to UC-3.2's postcondition — a cross-use-case dependency worth being aware of if either doc is revised independently.

## Known limitations (not changed this pass)

- A3's export-failure silence is a real, user-facing gap (no feedback at all on a failed CSV download) — flagged during verification, not fixed, since it wasn't explicitly requested and the fix (add a `catch`, surface an inline error, offer retry, ideally mirroring the report modal's own existing error-handling pattern) is contained but not zero-risk to do blindly without confirming the desired UX.
- The hardcoded "Content Quality & Compliance" placeholder values for non-admin roles are a genuine misrepresentation risk but a larger product decision (build the real computation for Contributor/Moderator, or relabel the panel to make clear it's admin-only insight) rather than a quick fix — left as-is.
