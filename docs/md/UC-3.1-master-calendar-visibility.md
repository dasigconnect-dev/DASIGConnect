# UC-3.1 Master Calendar Visibility

**Use Case ID:** UC-3.1

**Use Case Name:** Master Calendar Visibility (calendar view + drag-reschedule). The automated Facebook publishing pipeline that actually moves a submission into the `published`/`publish_failed`/`missed_review` states this calendar renders is its own use case — see [`UC-3.2-automated-facebook-post-publishing.md`](UC-3.2-automated-facebook-post-publishing.md); this doc no longer duplicates it, only what the calendar itself does with the result.

**Actor(s):** All three roles view the calendar (`GET /api/v1/calendar`, `isAuthenticated()`), but with different scope. **Moderator has the same full, network-wide calendar access as Administrator** — this is a real correction from an earlier draft of this use case, which implied Administrator-only full visibility with Moderator scoped down like a Contributor. In fact `CalendarService.getCalendarEvents` branches only on `"moderator", "admin" -> getAdminCalendar()` vs. everyone else — Moderator and Admin get identical, unfiltered, network-wide detail. Only Administrator and Moderator can drag-reschedule (`PATCH /submissions/{id}/reschedule`, `@PreAuthorize("hasAnyRole('ADMIN', 'MODERATOR')")`); Contributor cannot reschedule at all, only view.

**Precondition(s):** The actor is authenticated. For reschedule: the target submission is currently `scheduled` (any other status returns `409`).

## Main Flow — Calendar Visibility

1. Any authenticated user opens the calendar. The backend branches by role (`CalendarService.getCalendarEvents`, `CalendarController.getCalendar` — `GET /api/v1/calendar`).
2. **Moderator or Admin** (`getAdminCalendar()`): sees every submission with a scheduled slot or publish time network-wide, via `SubmissionRepository.findAllWithScheduledSlot()` (`scheduledAt IS NOT NULL OR publishedAt IS NOT NULL`, excluding `missed_review` and `draft`), always rendered in full detail (`CalendarEventDto.full()` — caption, description, contributor name, everything).
3. **Contributor** (`getScopedCalendar(user)`): sees two merged buckets —
   - A **network bucket** (`findAllCalendarVisibleSlots()`, statuses `scheduled`/`direct_post_scheduled`/`publishing`/`direct_post_publishing`/`published`/`published_manual`/`admin_direct_post`): rendered `full()` for their own institution and for the network-default institution ("DASIG Central Visayas"), and `masked()` (caption/description/contributor name nulled) for every other institution.
   - An **own-workflow bucket** (`findOwnCalendarWorkflowSlots(contributorId)`, statuses `publish_failed`/`direct_post_failed`/`pending`/`in_review`/`missed_review`, scoped to that Contributor's own submissions): always rendered in full detail and flagged `mine: true`, so a Contributor can track their own in-flight submissions even before they're calendar-visible to anyone else. On an id collision this bucket wins over the network bucket's entry.
4. `CalendarEventDto` also carries `originalScheduledAt` and `moderatorRescheduleCount` on `full()` events (needed by the frontend's client-side reschedule-cap pre-check, step 3 of the Reschedule flow below) — `masked()` events omit both (left at their default `null`/`0`), since a masked event never reaches the reschedule UI anyway.

## Main Flow — Drag-Reschedule (Admin/Moderator)

1. An Administrator or Moderator drags a `scheduled` event to a new date/time on the calendar (`CalendarScreen.handleEventDrop`).
2. The frontend first reverts a no-op drop (same slot) and a too-soon drop (within 1 hour of now — a client-side-only convenience check; the real minimum-lead guard rail is GR-H2, ≥2 hours).
3. **For a Moderator only** (Admin is exempt from both), the frontend mirrors the backend's cap/window rule for fast client-side rejection before ever opening the confirm modal: reverts with a toast if `moderatorRescheduleCount >= 2`, or if the new time is more than 1 day from `originalScheduledAt` (falling back to the event's current `scheduledAt` if `originalScheduledAt` is absent).
4. `CalendarRescheduleModal` opens for a written reason and confirmation; confirming sends `PATCH /submissions/{id}/reschedule` with `{ scheduledAt, overrideReason }`.
5. Backend (`SubmissionService.reschedule`): reloads the submission, requires status `scheduled`, re-checks the Moderator cap/window server-side (403 if either is violated — the client-side check above is a UX convenience, not the actual enforcement), then validates the new slot against the guard rails (`GuardRailService.validate`).
6. If the guard rails are clean, or the caller is an Admin supplying an override reason, the reschedule proceeds; the write itself is an atomic conditional `UPDATE` (`claimModeratorReschedule`/`claimAdminReschedule`), not a plain load-mutate-save — see the Concurrency note below.
7. The slot is reserved (`SlotReservationService.reserveLockedSlot`), a `SubmissionRescheduledEvent` is published, and the updated event returns to the calendar.

## Alternative Flows

- **A1 — Moderator Reschedule Cap & Window (added 2026-09-17, not in the original draft).** A Moderator may reschedule a given `scheduled` submission at most **2 times** (the count lives on the submission, `Submission.moderatorRescheduleCount` — not on the Moderator account, so it doesn't matter how many different Moderators do the rescheduling), and only within **±1 day of the slot it was originally approved at** (`Submission.originalScheduledAt`, snapshotted once by `ValidationService.approve()` at the moment status becomes `scheduled`, skipped for Fast-Track submissions since they have no slot to snapshot, and never touched by a later reschedule itself — anchoring to the *original* approved slot rather than the most recently rescheduled one prevents drift via repeated small moves). Hitting either limit is an unconditional hard stop for a Moderator with no override of their own — they ask an Administrator, who is exempt from both limits. A successful retry-onto-a-new-slot after a publish failure (`ManualPublishingService.retryWithNewSchedule`'s `publish_failed → scheduled` branch) re-baselines both fields to the retry's new slot, since that's effectively a fresh start, same as an original approval.
- **A2 — Guard Rail Hard Block on Reschedule.** If the new slot violates a hard guard rail (GR-H1/H2/H3), a Moderator cannot proceed at all — even with a written reason — and is told to ask an Administrator instead; only an Administrator can supply an override reason and proceed, which is audit-logged as `ADMIN_RESCHEDULE_OVERRIDE` with the violated rules, both slots, and the reason recorded.
- **A3 — Reschedule Reason Is Always Required, Even When Compliant (known frontend gap, not fixed).** `CalendarRescheduleModal` unconditionally requires a ≥10-character written reason to confirm *any* reschedule, including one that doesn't touch a guard rail at all. The backend only actually needs `overrideReason` when a hard guard rail is blocked (see A2) — a clean reschedule doesn't need one. This is a real gap against "proceeds automatically" for the compliant case; flagged but not addressed, since fixing the modal to conditionally skip the reason field wasn't in scope for the sessions that touched this feature.
- **A4 — Concurrent Reschedule Race (found and fixed 2026-09-17).** `Submission` has no `@Version`/optimistic locking, so the cap/window check above is an ordinary entity read — before the fix, two concurrent reschedule requests for the same submission could both pass that check before either one wrote, letting a Moderator's cap be exceeded by a race rather than a logic gap. Fixed by making the actual write an atomic conditional `UPDATE` (`SubmissionRepository.claimModeratorReschedule`/`claimAdminReschedule`, the same idiom `PublishingQueryService.claimForPublishing` already used for the publishing claim) — a claim that doesn't affect exactly 1 row now surfaces as `409 CONFLICT` ("This post was just changed by someone else") instead of silently proceeding.
- **A5 — GR-H1's Network-Wide Buffer Had No DB-Level Enforcement (found and fixed 2026-09-17).** GR-H1 (no two active posts within ±30 minutes of each other, network-wide) was only ever checked as a pre-write read in `GuardRailService`. `SlotReservationService`'s own comments incorrectly claimed a "unique index on (scheduled_at, institution_id)" already made this atomic — it didn't; `V1` only ever created a plain, non-unique index, so there was no DB-level protection at all, not even for two reservations at the exact same institution and exact same instant. A live diagnostic query against the database found one real instance: two already-`published` submissions 27 minutes apart that had silently slipped past GR-H1. Root cause of that specific pair (and 9 more like it network-wide): a submission's `locked` `SlotReservation` was never released once it actually published, so terminal submissions kept occupying the ±30-minute buffer forever. Fixed in three parts — `FacebookPublisherService.markPublished()` and `ManualPublishingService.complete()` now call `SlotReservationService.release()` on success; `V95__slot_reservation_conflict_exclusion.sql` first releases every pre-existing stale `locked` reservation belonging to a `published`/`published_manual`/`admin_direct_post` submission, then adds a genuine Postgres GiST exclusion constraint (`EXCLUDE USING gist (tstzrange(scheduled_at, scheduled_at + interval '30 minutes', '[]') WITH &&) WHERE (status <> 'released')`, deliberately with no `institution_id` term, matching GR-H1's network-wide scope) so the database itself now rejects any two conflicting reservations regardless of how the requests race. `publish_failed`/`direct_post_failed` submissions' locked reservations were deliberately left alone — still mid-recovery, not obviously safe to release. **A regression in that very fix, found and fixed the same day (V96 migration):** the V95 constraint was unconditional, which silently broke the Administrator's pre-existing, intentional ability to override a blocked GR-H1 slot (both on reschedule here and on `ManualPublishingService.retryWithNewSchedule`'s manual-publish retry) — `SlotReservationService.reserveLockedSlot()`'s own javadoc says it "bypasses guard rail validation (caller is responsible)," but after V95 the DB constraint rejected the override's `INSERT` anyway, regardless of the Admin's explicit reason. Fixed by adding an `admin_override` boolean column to `slot_reservations`, set only when `reserveLockedSlot()` is called specifically because a hard block was overridden (`reschedule()`'s `adminOverride` local, threaded through as a new 4th parameter), and scoping the exclusion constraint's `WHERE` clause to exclude those rows (`status <> 'released' AND NOT admin_override`) — this reopens the narrow race only for the override case itself (no worse than before V95 existed there), while every normal reschedule/submission stays hard-enforced.

## Postcondition(s)

Every authenticated actor sees a calendar reflecting their role's true scope: Administrator and Moderator see the whole network in full detail (including caption/description/contributor identity), Contributor sees their own institution and the network-default institution in full detail, every other institution masked to non-identifying fields, plus their own in-flight submissions regardless of institution. A `scheduled` submission can be moved by an Administrator or Moderator within their respective limits, with every write guaranteed to reflect only its own intended change even under concurrent requests — including, as of the GR-H1 fix (A5), against a submission scheduled or rescheduled through any other path, not just another reschedule. What happens after a submission leaves `scheduled` (publish success/failure, missed-slot detection) is UC-3.2's territory, not this one's.

## Not in the original draft at all

- The Contributor's "own-workflow bucket" — seeing their own `pending`/`in_review`/`publish_failed`/`direct_post_failed`/`missed_review` submissions on the calendar in full detail, flagged `mine: true`, even though these statuses aren't otherwise calendar-visible to anyone else.
- The Moderator reschedule cap and 1-day window (A1) and its atomic-claim race-condition fix (A4) — both added 2026-09-17, well after any original calendar-visibility draft.
- The precise guard rail inventory this reschedule flow enforces: GR-H1 (±30 min network-wide slot conflict), GR-H2 (≥2h lead time), GR-H3 (≤30 days out) as hard blocks; GR-S1 (institution-scoped, <3 unpublished) and GR-S2 (network-wide, <6/day) as soft warnings that don't block a reschedule at all (soft warnings only ever apply to new submissions, not reschedules of an already-approved one).
- The `CalendarEventDetailModal.tsx` variable named `isAdmin` actually means "Moderator or Admin" (`user.role === "moderator" || user.role === "admin"`) — functions correctly, just a misleading name for anyone reading the frontend code expecting it to mean Administrator specifically.

## Known limitations (not changed this pass)

- A3 (the reschedule reason always being required, even for a fully guard-rail-compliant move) is a real gap against the "proceeds automatically" expectation, left as-is — it was flagged during verification but never explicitly requested to be fixed.
- `CalendarEventDetailModal.tsx`'s `isAdmin` naming is confusing but not incorrect; left unrenamed since it wasn't the target of any specific fix request.
