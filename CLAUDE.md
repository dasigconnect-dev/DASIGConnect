# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**DASIGConnect** is a capstone project (Team `2526-sem2-it332-38`, CIT-U) - a web-based Social Media Content Workflow and Scheduling Management System for the **DOST Academe-Science and Innovation Group (DASIG)** under DOST Region 7.

It replaces ad hoc coordination between DASIG member HEIs with a structured workflow: contributors submit event content, validators review it, administrators approve/schedule it, and the system later publishes to the DASIG Facebook Page.

See `README.md`, `TASKS.md`, and `docs/` for project context, SRS, SDD, and task status.

## Architecture

DASIGConnect is a three-tier client-server system:

```text
React SPA (Vercel) -> Spring Boot REST API (Render) -> Supabase PostgreSQL + pgvector
                                                     -> Cloudflare R2 (S3-compatible object storage)
                                                     -> Facebook Graph API
                                                     -> Anthropic Claude
                                                     -> Voyage AI
```

**Object storage moved from Supabase Storage to Cloudflare R2.** `MediaStorageService`
wraps the AWS S3 SDK against any S3-compatible endpoint; config lives under
`app.r2.*` / `R2_*` (`R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`,
`R2_SECRET_ACCESS_KEY`, `R2_PUBLIC_BASE_URL`). The browser `PUT`s bytes straight
to an R2 presigned URL for upload, but reads go through **this backend's own
proxy**, not R2 directly (2026-09-13) — `getPublicUrl()` returns
`{BACKEND_PUBLIC_BASE_URL}/api/v1/media-files/<key>`, served by
`MediaProxyController` (unauthenticated, matching the R2 URL it replaces) via
`MediaStorageService.downloadObject()`. This exists because R2's "Public
Development URL" (`pub-*.r2.dev`) is explicitly documented by Cloudflare as not
for production use and can be disabled or rotated to a new hash at any time —
when that happened here, every previously-stored `media_assets.storage_url`
died simultaneously (DNS stopped resolving), breaking every media preview in
the app at once. `R2_PUBLIC_BASE_URL` is now used only to recognize
already-stored pre-migration URLs so deletes keep resolving an object key for
them (`deletePublicObject`/`objectPathFromPublicUrl`) — new URLs never use it.
**Production deploy needs `BACKEND_PUBLIC_BASE_URL` set** to the backend's real
public origin (defaults to `http://localhost:8080`, which only works locally);
existing rows still on the old R2 host need a one-time SQL backfill
(`UPDATE media_assets SET storage_url = REPLACE(storage_url, '<old R2 host>/', '<BACKEND_PUBLIC_BASE_URL>/api/v1/media-files/') WHERE storage_url LIKE '<old R2 host>/%'`)
— not run automatically, since the old host isn't knowable at build time. Supabase is now
**database only** (Postgres + pgvector). `DASIG_SUPABASE_SERVICE_ROLE_KEY` is kept
solely as a legacy read fallback in `ClaudeVisionClient` for old images still on
the private Supabase bucket.

### Backend - Spring Boot 4 / Java 21

- Entry point: `backend/src/main/java/com/dasigconnect/backend/BackendApplication.java`.
- Config: `backend/src/main/resources/application.properties`.
- Local env loading: `spring-dotenv` reads `backend/.env`.
- REST base path: `/api/v1`.
- Auth: stateless JWT through Spring Security and `JwtAuthenticationFilter`.
- Tenancy: institution scoping through `TenantScopeService` plus PostgreSQL RLS.
- DB migrations: Flyway in `backend/src/main/resources/db/migration/`.
- DB access: Spring Data JPA + Hibernate through HikariCP.
- Critical pool limit: keep Hikari max pool size at 5 for Supabase Session Pooler.

### Frontend - React 19 / TypeScript / Vite

- Entry: `frontend/src/main.tsx`.
- App shell: `frontend/src/app/App.tsx`.
- API clients: `frontend/src/api/`.
- UI: shadcn/ui, Radix UI, Tailwind CSS v4.
- Routing: React Router v7.
- HTTP: Axios with Authorization header managed by `setAuthToken`.
- Session expiry: `App.tsx` parses JWT `exp`, shows countdown banner near expiry, and opens the session modal at timeout.
- Media upload: browser requests a presigned URL from the backend, `PUT`s the file bytes directly to Cloudflare R2, then sends media metadata to the backend. No `@supabase/*` client or storage keys in the frontend.

### Module 1 — Accounts, Institutions, Sessions

- **UC-1.1 Administrator Account Management** — see [`docs/md/UC-1.1-administrator-account-management.md`](docs/md/UC-1.1-administrator-account-management.md). Invite/promote/deactivate/reactivate/delete/erase an Admin account; a 3-admin cap (`app.admins.max`) enforced uniformly across invite, accept, promote, and reactivate; promotion to Admin is a propose/confirm flow, not instant; Admin Owner transfer.
- **UC-1.2 Institution Management** — see [`docs/md/UC-1.2-institution-management.md`](docs/md/UC-1.2-institution-management.md). Create/edit/deactivate/reactivate/permanently-delete an institution; the protected network-default institution ("DASIG Central Visayas") is exempt from both deactivation and deletion; Contributor reassignment between institutions.
- **UC-1.3 Contributor Account Management** — see [`docs/md/UC-1.3-contributor-account-management.md`](docs/md/UC-1.3-contributor-account-management.md). Invite/deactivate/reactivate/delete/erase a Contributor account; Moderators may only manage invitations they personally sent; re-inviting any deactivated account (any role) is blocked and must go through Reactivation.
- **UC-1.4 Login & Session Management** — see [`docs/md/UC-1.4-login-session-management.md`](docs/md/UC-1.4-login-session-management.md). JWT sessions (8h TTL) carry role + tenant scope; session revocation is persisted (`revoked_tokens` table for single-token logout, `users.session_version` for account-wide), enforced inside `JWTService.extractClaims` for every caller; only a password **reset** (not an authenticated password change) invalidates other sessions; Facebook Messenger notification linking is a 10-minute link-code sent via Messenger (not OAuth), open to Moderators and Admins; Analytics is available to all three roles (role-scoped, not Admin-exclusive) — everything else under Admin Management/System Health/Audit Log/Page Settings/Watermark Configuration is Admin-only.
- **UC-1.5 Post Drafting & Templates** — see [`docs/md/UC-1.5-post-drafting-templates.md`](docs/md/UC-1.5-post-drafting-templates.md). The 3-step composer (Media → Details → Schedule) used by contributors, moderators, and admins; readiness checklist with a 0–100 score; built-in + personal Save-as-Template; autosave; withdraw. Scheduling guard rails are a **network-wide runtime switch** (`page_settings.guardrails_enforced`, toggled in Settings → Page, read via `GuardRailSettingsService` and surfaced to the composer through `/submissions/lookups`). It governs the _rules_ on a scheduled time, not whether one is picked: a Standard post always needs a future slot and a `SlotReservation`; when off, the ±30-min spacing / ≤6-per-day / ≥2h-lead / 8 AM–8 PM checks are skipped.
- **UC-1.6 AI & Text Tools Integration** — see [`docs/md/UC-1.6-ai-text-tools.md`](docs/md/UC-1.6-ai-text-tools.md). `POST /api/v1/ai/caption` (Claude `claude-haiku-4-5`, 30 s timeout, ≤4 images, >5 MB in-memory downscale) returns **one** caption for a chosen tone (`professional`/`community`/`energetic`); 30 requests/hour per user (in-memory limiter → `429`); 280-char prompt cap; interaction telemetry via `/ai/caption/log`. `FancyTextTool` is a button-opened panel (not auto-on-selection) with 5 Unicode styles + Plain revert. Both tools need a saved draft and work in Fast-Track; both are hidden only on read-only submissions. The stored-caption ceiling is **3000 characters** (code points) on both ends — frontend `CAPTION_CHAR_LIMIT` (`features/submission/utils.ts`, imported by `FancyTextTool`), backend `SubmissionService.MAX_CAPTION_CHARS` (`validateCaptionCharLimit`, 400 on create/update, 422 on submit). `ClaudeVisionClient.MAX_REQUESTED_CAPTION_WORDS = 2000` is a separate prompt-parsing guard on the requested word count, not the stored-caption limit. The AI caption context no longer includes a submission category — `Submission.category` was always `null` from the composer (`toPayload()` hardcodes `category: ""`; there is no category input field), so it was removed from `ClaudeVisionClient`/`CaptionGenerationService`'s Claude prompt-building end to end. `Submission.category` itself is untouched — still used by built-in post templates and UC-3.3 media-suggestion re-ranking.
- **UC-1.7 Media Attachment Rules** — see [`docs/md/UC-1.7-media-attachment-rules.md`](docs/md/UC-1.7-media-attachment-rules.md). Device upload (JPEG/PNG/WebP/GIF images, MP4/MOV/WebM video, ≤50 MB); library selection (UC-2.2); AI-suggested media (Voyage embedding, pgvector, 0.40 score floor, top 8, gated on ≥10 combined chars of event context); per-asset caption (≤500 chars) and image-only skip-watermark via the Media Caption modal; mixed image+video is accepted as a draft but fails automated publishing (`FacebookPublisherService`) and routes to the Approval Queue's Failed tab (UC-2.4) for manual recovery. **Album Auto-Match is now real AI matching**: `AIRecommendationService.suggestAlbum` (`POST /ai/submissions/{id}/suggest-album`) blends tag overlap with "closest existing asset" visual similarity (Voyage + pgvector, max score across a root album's assets, not a centroid) — confident (≥0.55) auto-applies with a reason badge, ambiguous (≥0.32) lists up to 3 ranked candidates inline in `AlbumCombobox`, otherwise the field is left for manual select/create.
- **UC-1.8 Engagement Helpers** — see [`docs/md/UC-1.8-engagement-helpers.md`](docs/md/UC-1.8-engagement-helpers.md). Peak-time recommendations (`EngagementRecommendationService`) come from real Facebook Graph API history (last 100 posts, reactions+comments+shares, 8 AM–8 PM window, Asia/Manila) — top 5 (day, hour) buckets by average engagement, needing ≥20 samples or a Tue/Wed/Thu 6 PM default is used; up to 3 future slots over a 30-day lookahead, each pre-filtered against guard rails (hard-blocked candidates excluded, not flagged); panel is skipped entirely for Fast-Track drafts and hidden outright if the Facebook analytics call fails. A manually-typed (non-recommended) time's soft guard-rail warnings now surface inline next to the date/time fields (`.sub-inline-warning`, gated on `lookups.guardrailsEnforced`) — same pattern already used for reviewer reschedules in `ValidationQueueScreen`/`ResolutionRetryModal`.
- **UC-1.9 Draft Submission** — see [`docs/md/UC-1.9-draft-submission.md`](docs/md/UC-1.9-draft-submission.md). `SubmissionService.submit()` moves `draft`/`needs_revision` → `pending` after `assertContentComplete` (title, date, caption, media, **album**) and, for Standard drafts only, a guard-rail re-check (`409` on conflict, e.g. UC-1.5's guard rails); Fast-Track skips the slot check entirely. Notifies **Moderators** (not Administrators) — T-01 in-app+Messenger for a standard submission, T-11 in-app+email+Messenger "urgent" for Fast-Track. Withdrawal is `pending`-only and blocked the instant a `ReviewLock` exists — the `POST /submissions/{id}/withdraw` route itself was missing from `SubmissionController` (the service method existed and was tested, but nothing ever called it, so withdrawal always 404'd); fixed by adding the endpoint. A concurrent slot-conflict (`409`) at submit time now redirects the composer back to Scheduling instead of a generic toast, and Fast-Track submissions now sort to the top of the active Approval Queue (UC-2.4) on both ends — `findValidationQueue` orders `fastTrack DESC, scheduledAt ASC NULLS LAST, submittedAt ASC`, and `ValidationQueueScreen`'s own sort mirrors it (not applied in the "All" history tab).
- **UC-1.10 Moderator Account Management** — see [`docs/md/UC-1.10-moderator-account-management.md`](docs/md/UC-1.10-moderator-account-management.md). Network-wide (institutionless) Moderator invite/deactivate/reactivate/delete/erase; a Moderator may invite a Contributor to any institution but only manage invitations they personally sent; direct lateral role change between Contributor and Moderator.

- **UC-2.1 Library Uploads & Albums** — see [`docs/md/UC-2.1-library-uploads-albums.md`](docs/md/UC-2.1-library-uploads-albums.md). Standalone Media Library upload (`isAuthenticated()` — all three roles, not Contributor/Administrator-only): same 7-format/50MB validation as the composer, ≥1 tag required. Nested folder-style albums per institution (`ensure-path`, re-parenting with a cycle guard) plus a shared default-institution library. Grid browsing (`list`), meaning-based search (`search` → Voyage embedding + pgvector, keyword fallback), sort (newest/oldest/name/size), grid/list toggle, Asset Detail Panel — all open to all three roles, Network View to Moderator+Admin (no actual on/off toggle — it's permanently on for those two roles). Both real gaps found this session are now fixed: **manually-added tags are searchable** (`MediaAssetService.loadAllTagLabels` batch-fetches every tag, manual or AI, for both `list()`'s query filter and `/search`'s keyword fallback; semantic _ranking_ still only reflects a tag present at original classification time, since nothing re-embeds on tag edit), and **Network View access is now actually audit-logged** (`POST /media-assets/network-view/log` → `MEDIA_NETWORK_VIEW_ACCESSED`, fired once per browser session). There is no trash/deleted-items view or restore capability anywhere in the app — the delete confirmation modal tells the actor the removal is permanent, and the 30-day window is an internal safety buffer before hard-purge, not a self-service undo feature.
- **UC-2.3 Notifications** — SSE stream + REST CRUD, event-triggered in-app/email notifications, sidebar unread badge.
- **UC-2.3 Media History & Asset Lifecycle** (SRS numbering — collides with "UC-2.3 Notifications" above; see the numbering note) — see [`docs/md/UC-2.3-media-history-asset-lifecycle.md`](docs/md/UC-2.3-media-history-asset-lifecycle.md). Used In block (current relationship links + historical `MEDIA_ASSET_REUSED` audit rows for deleted submissions, concatenated — not a true single chronological merge), tiered deletion (`pending`/`in_review`/`scheduled` hard-blocks, `draft`/`needs_revision` needs `force=true`, terminal/unused deletes freely), `[Submission Deleted]`/`[Asset Deleted]` placeholders, exact-SHA-256 duplicate detection only (no visual-similarity signal despite that existing elsewhere for AI recommendations).
- **UC-2.4 Role-Scoped Analytics** — `/analytics` is reachable by all three roles; Contributor sees own submissions only, Moderator sees their institution, Admin sees network-wide with an institution filter.
- **UC-2.4 Approval Workflow** (SRS numbering — collides with "UC-2.4 Role-Scoped Analytics" above; see the numbering note) — see [`docs/md/UC-2.4-approval-workflow.md`](docs/md/UC-2.4-approval-workflow.md). `ValidationService`'s own class comment names this UC. Moderator is network-wide (not institution-scoped, despite that being the intuitive assumption); self-submission review is unconditionally blocked with no governance exception (the stale `requestRevision`/`reject` comment that used to claim otherwise is fixed 2026-09-17); A7 media-load-failure recovery now exists (`FacebookPostImage` retry-on-error state, same day); edit validation covers media/schedule but not watermark rules; the contributor's edit-during-review notification is a separate event, not a flag embedded in the approval notification. **Real bug fixed the same day, found while verifying this UC, not from the original draft:** `ValidationService.logsSinceLock()` scoped the combined edit-diff/severity to "since the most recent `lock_acquired` row" — a reviewer who edited, then released or lost the lock before a terminal action, then later reacquired it and approved with no further edits, got `edited=false` recorded and the contributor was never told the submission had been edited, even though it genuinely had been. Now scopes to the whole review cycle (since the last terminal action, or start of history), surviving any number of lock releases/reacquisitions within one cycle while still resetting cleanly after a real terminal action.
- **UC-2.5 Watermark Configuration** — see [`docs/md/UC-2.5-automated-watermarking.md`](docs/md/UC-2.5-automated-watermarking.md). **Network-wide default only — institution-specific overrides were dead code and have been removed (2026-09-17).** They never worked: `WatermarkConfigurationService.get()`/`.save()` ignored the `institutionId` they were passed and always read/wrote the single global config, and `WatermarkApplicationService.resolveConfiguration()` never looked at the submission's institution either — scaffolding for a feature apparently built partway then descoped. `findByInstitutionId`, the DTOs' `institutionId`/`institutionName`/`isOverride` fields, the frontend's unused `institutionId` plumbing, and the orphaned `WATERMARK_OVERRIDE_REMOVED` audit action are all gone; `WatermarkConfigurationRepository.deleteByInstitutionId` is kept, but only because `InstitutionService`'s hard-delete path still needs it for FK cleanup (the `institution_id` column and its FK stay in the DB unused, same "don't force a migration to drop it" precedent as `PageSettings.facebookPageId`). Also: watermarking happens at **publish time**, not at approval — editing the config between approval and a Standard submission's scheduled publish time does affect that pending post; a missing config falls back to a hardcoded default text watermark baked into the code, not a true unwatermarked publish. **A rendering failure is now audited and notified (2026-09-17, was silent before)**: `WatermarkApplicationFailedEvent` → `NotificationEventListener.onWatermarkApplicationFailed` emails/notifies every Admin, and `AuditLogService` records `PUBLISH_WATERMARK_FAILED` — publishing itself still isn't held up by it (a missing watermark is cosmetic; a missed scheduled post is not). **The generated watermarked derivatives in R2 are now cleaned up too (2026-09-17)** — they used to live outside the `media_assets` retention lifecycle entirely and accumulate forever; a new `GeneratedWatermarkPurgeJob` (daily, `app.watermark.purge-cron`) sweeps `generated/watermarked/` and deletes anything past `app.watermark.generated-retention-days` (default 3 days — Facebook only fetches the URL once, at publish time), via `MediaStorageService.purgeExpiredGeneratedWatermarks`, registered like every other background job in `ManualJobRunner`/`SystemHealthService`.

### Module 3 — Publishing & Exceptions (UC-3.x) — _UC-3.1 and (per a second, SRS-drafted numbering series — see the numbering note below) UC-3.2 Automated Facebook Post Publishing have living, code-verified docs; the rest below have not been independently re-verified this session_

- **UC-3.1 Master Calendar Visibility** — see [`docs/md/UC-3.1-master-calendar-visibility.md`](docs/md/UC-3.1-master-calendar-visibility.md). Role-scoped calendar view and drag-reschedule only — the automated publishing pipeline that actually moves a submission through `scheduled`/`published`/`publish_failed`/`missed_review` is UC-3.2, not duplicated here anymore (it used to be, making this doc unnecessarily heavy; split out 2026-09-18). Moderator has the same full, network-wide calendar access as Admin (`CalendarService.getCalendarEvents` — `"moderator", "admin" -> getAdminCalendar()`) and can drag-reschedule a `scheduled` post, but cannot override a hard guard-rail block (403, told to ask an Admin) and, since 2026-09-17, is capped at **2 reschedules per submission** (not per-Moderator — the count is on the submission) and **±1 day of the slot it was originally approved at** (`Submission.originalScheduledAt`, snapshotted once in `ValidationService.approve()`, never touched by a later reschedule — anchoring to the *original* slot rather than the most recent one prevents drift via repeated small moves). Admin is exempt from both caps. Enforced in `SubmissionService.reschedule()`; mirrored client-side in `CalendarScreen.handleEventDrop` so a capped-out drag fails fast with a clear message instead of round-tripping a 403 through the confirm modal. Fixed alongside this: `CalendarRescheduleModal`'s error extraction read `response.data.message`, a field that never exists — the axios interceptor in `authApi.ts` collapses the backend's `{error: {code, message}}` envelope down to a plain string at `response.data.error`; every backend rejection reason (guard-rail blocks, the new caps, anything) was silently swallowed in favor of a generic fallback. A close look found exactly 2 more frontend files with the same broken pattern — `AuditLogScreen.tsx` and `AccountSettingsScreen.tsx` — both fixed the same way; several others that looked similar at a glance (`ValidationQueueScreen.tsx`, `useValidationQueue.ts`, `MediaRepositoryScreen.tsx`, `useMediaAssets.ts`) already check `.error` before falling back to `.message` and were confirmed safe. **A bug found the same day**: `ManualPublishingService.retryWithNewSchedule()`'s `publish_failed → scheduled` branch (a fresh slot chosen after a publish failure) left `originalScheduledAt`/`moderatorRescheduleCount` untouched — a submission that had already used up its cap, or drifted far from its original slot, before failing to publish came back from a successful retry still capped out or immediately outside the 1-day window of a now-irrelevant old slot. Fixed by resetting both there, since a successful retry-onto-a-new-slot is effectively a fresh baseline, same as the original approval. **A race condition found and fixed the same day**: `Submission` has no `@Version`/optimistic locking, so the reschedule cap/window check was a plain read-check-write — two concurrent reschedule requests for the same submission could both pass the check before either wrote, letting a Moderator exceed the 2-reschedule cap. Fixed by making the actual write an atomic conditional `UPDATE` (`SubmissionRepository.claimModeratorReschedule`/`claimAdminReschedule`, mirroring `PublishingQueryService.claimForPublishing`'s idiom) — a claim that doesn't affect exactly 1 row now throws `409 CONFLICT` instead of silently proceeding. **A second, more fundamental race found and fixed the same day (V95 migration)**: GR-H1 (no two active posts within ±30 minutes of each other, network-wide) was only ever enforced by a pre-write read in `GuardRailService` — `SlotReservationService`'s own comments incorrectly claimed a "unique index on (scheduled_at, institution_id)" already made this atomic, but `V1` only ever created a plain, non-unique index; there was **zero** DB-level protection. A live-DB diagnostic query found 1 real pair of already-`published` submissions 27 minutes apart that had silently slipped past GR-H1, root-caused to `locked` `SlotReservation` rows never being released once their submission actually published (11 of 15 still-`locked` rows network-wide). Fixed: `FacebookPublisherService.markPublished()`/`ManualPublishingService.complete()` now release the slot on success; `V95__slot_reservation_conflict_exclusion.sql` cleans up existing stale locks for terminal submissions, then adds a Postgres GiST exclusion constraint (network-wide, no `institution_id` term, matching GR-H1's own scope) so the database itself now rejects any two conflicting reservations regardless of how requests race. (First attempt at this migration failed — Postgres rejected `timestamptz + interval` inside the index expression as non-`IMMUTABLE`; fixed by wrapping `EXTRACT(EPOCH ...)` in a custom `IMMUTABLE` SQL function and building the exclusion range on whole seconds instead.)
- **UC-3.2 Automated Facebook Post Publishing** (SRS numbering — collides with "UC-3.2 AI Caption Generation" below; see the numbering note) — see [`docs/md/UC-3.2-automated-facebook-post-publishing.md`](docs/md/UC-3.2-automated-facebook-post-publishing.md). Scheduled Facebook Graph API publishing: `PublishingSchedulerJob` (every minute, 5-min lookback) claims a submission (`scheduled → publishing`) via an atomic conditional `UPDATE` *before* any Graph API call — this is the actual double-publish safeguard, unmentioned in the original SRS draft entirely — then publishes 2-step photo (stage each image unpublished, including its own per-asset caption, then one `/feed` call) or single-call video, retrying up to 3 times with backoff. Fast-Track publishes asynchronously via `FastTrackPublishingListener` (`@TransactionalEventListener(AFTER_COMMIT)` on `SubmissionApprovedEvent`), bypassing the cron job entirely rather than being inline inside `ValidationService.approve()`. **Real corrections found verifying this UC against its SRS draft (2026-09-18):** the draft's single "missed-window → PUBLISH_FAILED" flow is actually two distinct sweeps in `StaleSubmissionDetectorJob` (every 5 min) with two different outcomes — an already-`scheduled` submission whose scheduler pass never ran goes to `publish_failed` as the draft says, but a submission that was never even approved before its slot passed goes to a separate `missed_review` status instead, releasing its slot and re-entering the Approval Workflow from `pending` rather than the Failed tab's manual-publish flow; the draft's claimed "consolidated notification listing unresolved photo IDs with a link to the Facebook Media Manager" on a partial-staging cleanup failure doesn't exist anywhere in the code — a failed `DELETE` of a staged photo is only ever `log.warn`'d, with the staged IDs recorded in `PublicationAttempt.photoIdsStaged` but never surfaced to the admin UI; the draft's "T-08" token-expiry alert only covers the pre-expiry warning (`token_expiring`) in code, not the 24h/48h escalation sequence (which reuses `token_invalid` and has no T-number of its own); and the draft's "±5-minute / ≥95% publish accuracy" postcondition is confirmed aspirational SRS prose with no corresponding metric anywhere in the code. One draft claim that looked aspirational but wasn't: "analytics within 60 seconds" is a real, fixed 60-second `@Cacheable` TTL on the summary endpoint (`MetricsAggregatorService.summary`), not live reads — no eviction is tied to a publish event, so it's a real (if incidental) upper bound.
- **UC-3.2 AI Caption Generation** — Claude Vision-based caption suggestions with instruction-vs-draft-refine intent detection (typing a directive vs. a draft caption changes how Claude responds).
- **UC-3.3 AI Media Suggestions** — Voyage (`voyage-4-lite`, 1024-dim) embeddings + pgvector similarity search with hybrid category/tag/recency re-ranking, surfaced in the Submit Content media picker's AI Suggestions tab. Contributor-facing category/tag AI suggestion (as opposed to media suggestion) is intentionally out of scope.
- **UC-3.4 Manual Publishing Fallback (Resolution Center)** — a 3-step guided manual-publish workflow for submissions the automated pipeline couldn't post, with a 2-hour abandonment window.
- **UC-3.5 Administrator Exception Handling** — a 5-tab Resolution Center hub covering validation timeouts, override requests, admin direct posts, and Facebook token re-authentication.

## Key Design Decisions

- JWT auth is stateless; do not introduce server-side sessions. Revocation, however, is DB-backed on purpose (`revoked_tokens` for single-token logout, `users.session_version` for account-wide) — enforced in `JWTService.extractClaims` so it survives restarts and holds across instances. Don't move it back into an in-process map.
- Tenant isolation is enforced in application services and PostgreSQL RLS.
- Flyway owns schema changes. Add migrations instead of relying on Hibernate DDL.
- Do not edit generated files under `backend/target`; fix migration conflicts in `backend/src/main/resources/db/migration`.
- `BackendApplication` custom Flyway/diagnostic beans are gated by `spring.flyway.enabled`; tests depend on this isolation.
- `MediaAsset.embedding` is not Hibernate-mapped because pgvector `VECTOR(1024)` is handled through native queries.
- AI Media Library now has a migration path toward `media_asset_embeddings` with separate `embedding_type` values (`image`, `semantic`, `keyframe`). Do not drop the old `media_assets.embedding` column until uploads, backfill, and suggestion search have been verified on the new table.
- Media upload: the frontend gets a presigned `PUT` URL from the backend, uploads the bytes directly to **Cloudflare R2** (S3-compatible, via `MediaStorageService`), then posts metadata to the backend. The backend never receives multipart file bytes. Object storage config is `app.r2.*` / `R2_*`; Supabase is database-only now.
- Submission media ordering is controlled by `submission_media_assets.display_order`; publishing queries already load assets ordered by this field. Use `PATCH /api/v1/submissions/{id}/media/order` for saved draft media reorder instead of mutating media asset records.
- Publishing is now claimed before any Facebook Graph API call. Preserve the atomic `scheduled -> publishing` / `direct_post_scheduled -> direct_post_publishing` transition so overlapping scheduler runs or multiple app instances cannot publish the same submission twice.
- Fresh Supabase `public` schemas should baseline Flyway at version `0`, not `1`; otherwise V1 is skipped and Module 1 tables are never created.
- Invitation links are treated as superseded when a fresh invite/resend is issued for the same email; do not leave multiple open invite links for one pending account.
- The frontend should display institution names from `GET /api/v1/me`; email-domain guessing is only a fallback.
- Do not increase HikariCP max pool size past 5 unless the Supabase plan/pooler changes.
- Do not log JWTs, passwords, reset tokens, invitation tokens, or API keys.
- `BackendApplication.flyway()` calls `repair()` then `migrate()` explicitly. Do not add `outOfOrder=true` or `validateOnMigrate=false` — fix schema history issues by renumbering migration files instead.
- When a migration file was never applied to a shared DB but a higher-version migration already was, do not reuse the old version number. Create new files at the next available version number.
- V4 creates `asset_tags` with columns `(asset_id, tag, source)`. V17 drops and recreates it with `(media_asset_id, label)` to match the `AssetTag` entity. Do not revert V17.
- Notification inserts in `SubmissionService.submit()` (T1 — notify validators) are wrapped in try-catch. This is intentional: a notification failure must never roll back the PENDING status transition.
- **The connected Facebook Page is DB-driven, not env-driven (2026-09-13).** `FacebookPageToken.isActive` marks the one row the system currently publishes to; `FacebookPublisherService`/`FacebookEngagementAnalyticsClient`/`MetricsAggregatorService` all resolve it dynamically per call (`pageTokenRepository.findFirstByIsActiveTrue()`), never from a cached field. `FACEBOOK_PAGE_ID`/`FACEBOOK_PAGE_ACCESS_TOKEN` are a **one-time bootstrap only** — `FacebookPublisherService.bootstrapTokenFromEnvIfEmpty()` seeds a row from them only if `facebook_page_tokens` is completely empty (a brand-new deploy); once any row exists, env vars are never read again, even across restarts/redeploys. Three ways to change things, all in Settings → System Health → Tokens, all audit-logged: (1) OAuth re-auth (`TokenManagementService.initOAuth`/`handleCallback`, `TOKEN_REAUTHORIZED`) — the CSRF `state` param is a **stateless, HMAC-signed token** (tokenId + expiry + signature, verified with no server-side storage at all), not an in-memory session; it used to be a `ConcurrentHashMap` that broke ("Invalid or expired OAuth state") any time the backend restarted between clicking Reauthorize and Meta's redirect back — a redeploy, or a free-tier instance spinning down mid-flow — since that map doesn't survive a process restart or span multiple instances — and (2) pasting a raw token (`setManualToken`, `PUT /system-health/tokens/{tokenId}/manual`, `TOKEN_MANUALLY_SET`) both just refresh the token for the _currently connected_ page (admin-only, both validate the token against Graph API — `GET /{page-id}?fields=id` — before persisting, so a bad/mismatched paste gets an immediate `400` instead of silently breaking publishing); (3) **Connect a Different Page** (`connectPage`, `PUT /system-health/tokens/connect`, `FACEBOOK_PAGE_CONNECTED`) is the only way to change _which_ page is targeted, and it's gated to `JwtUserDetails.adminOwner()` — the single Admin Owner from UC-1.1 — not just any admin. It validates the new token the same way, deactivates every other page's row, and creates-or-reactivates the target page's row (never duplicates — `page_id` is unique). The frontend mirrors this: `User.adminOwner` (populated from `/me`'s `UserProfileResponse.adminOwner`) gates whether the "Connect a Different Page" card even renders, but the real enforcement is server-side. `PageSettings.facebookPageId` (Settings → Page Settings) used to _look_ like a page-switching control but was fully dead — nothing ever read it except the DTO round-trip itself — so it was removed from the API/DTOs/UI entirely; the column stays in the DB unused, same as the legacy watermark columns on that same entity, to avoid a migration.
- `SubmissionService.submit()` reconciles attached media with the finalised post: a new upload (STAGED, or any album-less asset — a real library pick always has an album) is bound to the institution, filed into the album resolved from `submission.albumName` (existing root album by name, else a new one) via `resolveSubmissionAlbum`, and set to PROCESSING for the AI pipeline; a library-picked asset keeps its original album. Both get the post's media tags (`applySubmissionMediaTags`, `manual` source, deduped by label). Do not re-home a library pick's album on submit.
- `MediaAssetRepository`'s native (`nativeQuery = true`) queries that map results onto the full `MediaAsset` entity must list every entity-mapped column explicitly and be updated whenever a new column/field is added to that entity (Hibernate has no `SELECT *` fallback for a native-to-entity mapping with an explicit column list) — `findNeedingEmbedding()` (used by `EmbeddingReconciliationJob`) was written before migration V92 added `content_hash`, so its SELECT list never included it; every embedding-backfill run threw `InvalidDataAccessResourceUsageException: Unable to find column position by name: content_hash` trying to hydrate that row. Fixed by adding `content_hash` to the SELECT list. There's no repository-level DB test suite in this project (all existing tests are Mockito unit tests), so this class of bug isn't caught by `./mvnw test` — double-check any new/edited native query against the entity's full column set by hand.
- **Publishing mode (Live Event/Fast-Track vs. Scheduled) is fixed during editing by default; only an Admin can override it, and never Scheduled→Live except through one specific path (2026-09-15).** Two places let a Moderator/Admin edit an already-submitted post, and both used to silently flip Live→Scheduled the moment a date/time was touched, because their edit forms had no `fastTrack` concept at all:
  - **Review Queue inline edit** (`ValidationService.edit`, `POST /validation/{id}/edit`): now rejects `dto.getFastTrack() != null` from a non-admin with `403` — a Moderator's edit can never change the mode, only an Admin's can. `ValidationQueueScreen`'s edit form mirrors this: the Schedule tab shows a static "Live Event"/"Scheduled" badge for everyone, but only an Admin sees it as an interactive Schedule/Live Event pill (`sub-mode-toggle`, same component as the composer's). Date/time fields are hidden entirely while the mode is Live.
  - **Publish Failed retry** (`ManualPublishingService`, Resolution/Failed tab): `retry()` (replays the exact same mode — was completely unreachable from the frontend until this fix, since the "Retry" button was wired to always open the new-schedule modal instead) now fires `SubmissionFastTrackRetryEvent` for a Fast-Track submission, because `PublishingSchedulerJob`'s cron requires a non-null `scheduledAt` and Fast-Track submissions never have one — without this, a Live retry would sit in `scheduled` status forever, never actually republished. `retryWithNewSchedule()` now clears `fastTrack` whenever it succeeds (giving a submission a specific time is inherently a Live→Scheduled conversion) and is Admin-gated when the submission was Fast-Track (a Moderator can still freely reschedule an already-Scheduled item — no mode change there). New `retryAsLiveOverride()` (`POST /resolution/{id}/retry-as-live`) is the only way to go the other direction, Scheduled→Live, and is Admin-only unconditionally. `ResolutionRetryModal` shows the same interactive toggle as Review Queue, Admin-only; a Moderator retrying an already-Live item skips the modal entirely (one click, no schedule to pick).
  - `FailedPublicationDto`/`FailedPublication` (frontend) gained a `fastTrack` field so the UI can tell which mode a failed item was in — it didn't carry this before.
- **`app.facebook.oauth-redirect-uri` must never fall back to a bare `localhost` literal (2026-09-15).** It used to default to `http://localhost:8080/api/v1/facebook/oauth-callback` when `FACEBOOK_OAUTH_REDIRECT_URI` wasn't set — harmless locally, but on a deploy that forgot to set the env var, `TokenManagementService.initOAuth` would build a Facebook "Authorize" URL pointing at `localhost:8080`, so clicking Reauthenticate in production always failed silently on Meta's side (or callback-error, depending on whether that literal happened to also be whitelisted). Fixed by defaulting off `${app.backend.public-base-url}` instead, which is already required to be set correctly per environment (same var the media proxy depends on) — a missing `FACEBOOK_OAUTH_REDIRECT_URI` now falls back to the right backend origin instead of localhost. Still set `FACEBOOK_OAUTH_REDIRECT_URI` explicitly whenever the redirect URI whitelisted in the Meta App differs from `BACKEND_PUBLIC_BASE_URL` (e.g. a dev/staging API domain) — the default is a safety net, not a replacement for keeping the Meta App's whitelist and this value in sync.
